High level ideas.


 Drifting必须服务于写作。更进一步，是小说创作。更进一步，是复杂的小说创作。
 必须支持所有的常用小说工作流。另外，AI可以弥补很多。
 
### 传统word写作痛点

 1. 全书大纲概览不方便，需要单独大纲文件。修改大纲极其繁琐。
	 1. 各种大纲视图
	 2. 模仿macOS salari的cmd+shift+\的视图，但展示相连的graphview。
	 3. 随时调起的时间线
	 4. 自定义章节的关系，如因果等
 2. 书籍元素管理，难以追踪，更新不方便，多版本同步。
	 1. 单独抽象
	 2. 自动添加，自动追踪、自动收集信息 - on device LLM
		 我需要智能地识别用户输入的内容，然后提供多种可能的tab选项。比如：
		1.  出现新的角色，看起来很重要，tab添加为element
		2. 某个角色发生了重要变化，tab来patch 现存的element
		3. 新写的东西和element的设定有冲突，提示处理冲突
	 3. 双向连接，网状结构。
	 4. 渐进版本控制 - 横向是故事阶段，纵向是历史快照
	 5. 便捷检索 - 高阶搜索功能
	 6. 选中文本 - 悬浮menu - 关联文本来patch element，并允许额外添加描述
		 1. on device LLM 辅助这个
 3. 版本控制，旧版本覆盖就没了，需要复制一堆。
	 1. 自动备份 - 类似timemachine的体验
	 2. 本地真源 - local first， 后端主要负责存数据和llm api调用。
 4. 信息管理，碎片信息灵感到处丢
	 1. 分类bucket管理，队列抽取
	 2. 自动匹配
 5. app内部做research和找参考
	 1. 允许导入reference随时观看，并接入os原生api
	 2. ai根据要写的东西，搜集材料，然后保存。
 6. 多端同步随手切换
	 1. 得做electron桌面端，加移动端。web感觉不对。
	 2. CRDT冲突合并
	 3. 暂时不需要多人协作，只需要用户自己的多设备同步
 7. 自己写缺少反馈，云端LLM api来处理。
	 1. copilot编辑，给出意见
	 2. copilot市场调研
	 3. 根据用户想写的东西的目标，语义搜索，从经典作品中找出相似的片段来参考。
		 1. 直接api调用，让服务方搜project gutenberg之类的就行。不需要自己建向量数据库。
		    https://chatgpt.com/share/695f1ee8-f954-8007-a8e1-64ded661cb83
	4. 工作流：选文本（可选） - 选意图 - 给参考
	5. agent来检查plot hole，角色行为一致性等等。得整合一个agent进去。
8. 和其他软件使用习惯不同
	1. 快捷键直接对齐主流浏览器。故事线切换之类的逻辑对齐tab group之类的。
	2. vscode的一些快捷键也借鉴。

旧时代的写作app太笨重，复杂；新时代的app不懂写作的内在逻辑，浅薄。
