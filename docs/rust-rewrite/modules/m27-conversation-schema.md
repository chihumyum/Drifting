# M27：对话文档结构提案（请 F1 审）

2026-11-08。这是 M27 使用的向后兼容新增结构，待 F1 审核纳入 `loro-schema.md`。旧的书目、正文、模板结构和创世字节不改；`meta.v` 仍为 2。

## 文档与内容

每个对话一篇 `conversation:<对话 id>`，归属的书由 F2 的文档记录保存。它没有正文编辑配置，不计字数、不进正文搜索、稿件导出和 Markdown 文件夹。新的 `ConversationId`、`DocId::Conversation`、`DocKind::Conversation` 在 `dr-model` 登记。

创世只写 `meta.v = 2` 和 `meta.doc = conversation:<id>`，写入者仍用 F1 的确定创世对等方算法，时间戳为 0。根列表 `entries` 只追加不可变的 JSON 字符串；没有原地编辑、删除或重排接口。每条记录是：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | 非空字符串 | 来源日志事件的稳定身份，运行时使用 `session:sequence` |
| `session` | 非空字符串 | 本机运行的随机全局唯一身份；记录这个身份不表示同步运行日志 |
| `turn` | u32 | 运行内的轮次 |
| `kind` | 字符串 | `user`、`assistant`、`thinking`、`tool_call`、`tool_result`；未知值保留 |
| `payload` | JSON 值 | 由 M27 的对应事件投出的内容，保留 M28 所需的签名思考块、工具参数等结构 |

只有已落盘日志事件能够投出记录。界面从日志事件还原本机运行；对话文档是可同步的内容投影，不是另一套本机消息表。权限请求、运行状态、取消等本机控制事件不写入此文档。逐次用量事件不单独投影；助手消息保留其最终用量汇总。

## 追加、重放与合并

> F1 第七轮改了这一节里的两点：同一身份内容不同的记录现在收下、读第一条并报出来，不再报错；导入校验改成只看更新自己的操作（删除、改身份、缺依赖就拒）。以 [loro-schema.md](../loro-schema.md)「对话文档」和下面「待协调」为准。

`id`、`session` 和 `kind` 都是非空、无控制字符且最多 256 字节的字符串；运行时使用 UUID 会话身份，为 `:sequence` 留出余量。追加前按 `id` 检查：没有则加到列表末尾；相同内容已经存在则不写任何变更；同一身份对应不同内容时报错。Loro 列表负责并发追加的顺序收敛。两台设备并发投出同一个日志事件时，列表可能包含两份相同的不可变值，读取按第一次出现的身份去重；冲突内容报错，不默默选其中一份。公开 API 不允许删除、覆盖或重排；`ConversationDoc::import` 先在副本验证，拒绝删除、修改、重排已有记录以及同身份的冲突。F3 的 `library_options` 已把 `conversation::validate_update` 装入 F2 的 `validate_import` 回调，在持有者线程上、实际导入前校验。Loro 本身不是不可信写入者的访问控制系统。

`ConversationDoc` 提供独占写入、载入、导入、导出和版本；`BorrowedConversation` 在 F2 持有的文档上提供类型化追加与读取，提交仍由持有者负责。追加事务使用 F1 的来源与提交约定，不能绕过 F2。

## 与其他模块的最小衔接

- F3 的正文命令、编辑会话、历史正文点和人物链接排除对话；对话导入走普通 F2 持有者，不经过正文修复，不发布正文事件。
- F2 的类型无关导入校验回调在持有者线程调用，避免校验和导入之间插入另一次写入。
- `dr-index` 给对话写空索引，不计数也不反复标成待重建。
- `.driftingbook` 仍携带对话文档；导入成新书时只改文档身份和创世对等方，`entries` 中的 JSON 字节保持不变。历史消息里的旧对象 id、工具参数和思考签名不会被改成新书的 id。运行日志和本机权限不在书文件里。

## 测试

`dr-doc` 覆盖创世、重开、借用、重放去重、不可变内容、并发追加收敛、未知内容保留和非法导入；`dr-workspace/tests/conversation.rs` 覆盖非正文边界和真实持有者的同步校验；`dr-index` 验证空索引；`dr-export` 用真实书文件验证复制后内容不变。

## 待协调

- **F1（第七轮已审，2026-11-08）**：结构已纳入 [loro-schema.md](../loro-schema.md) 的「对话文档」，记成 v2.2（向后兼容，`meta.v` 仍是 2）。文档种类、id 的形状、创世、只追加、按事件身份去重、未知内容保留都对。改了四处，测试和不变量（`CONVERSATION-APPEND` / `-HISTORY` / `-READ` / `-NOT-PROSE`）一起：
  1. **读取不再因内容失败**。一条读不懂的记录（以后版本的信封、不是 JSON、不是字符串），或同一身份两份不同内容，原来会让 `entries()` 和 `ConversationDoc::load` 报错：整篇对话打不开，也收不了同步，旧版本还会拒掉新版本的全部更新。现在读不懂的跳过并保留，同一身份读列表里第一条，两种都报在 `problems()`。`entries()` 的签名没变，只是不会再因内容报错。
  2. **导入校验只看更新自己的操作**。原来比的是导入前后的状态，可每台设备导入前见过的不一样：没见过某条记录的设备会收下「插入又删掉它」的更新，见过的设备拒绝，两边永久分叉。另外，先送删除（依赖没到，Loro 先挂着）、再送它依赖的插入，删除会不经检查生效。现在的规矩是：`entries` 上有删除（改和挪也是删加插）就拒；创世以外的人改 `meta.v` / `meta.doc` 就拒；依赖本机还没有的变更也拒。`meta` 别的键、别的根容器、读不懂的记录照收，留给以后的版本。
  3. **同一身份内容不同的记录不再拒收**。只有程序出错才会出现这种记录。拒收保护不了数据，却会挡住那台设备之后的全部更新。现在收下，读第一条，并报出来。
  4. **分派补了两处**：`BookView::owns_prose` 原来对对话返回假，存储清理没主人的正文时会把对话删掉，现在认它属于书；`project_todo` / `projected_todo` 原来把对话、模板、书目文档当成章节，现在只收书的正文。另外记录的事件身份、会话、种类改用 `dr_model::id::check_id` 检查，原来借用的是 `ConversationId::parse`，规则一样。
  - 顺带：2000 条、约 4 MB 文字时，追加一条 31 ms → 1.8 ms，校验一份更新 123 ms → 20 ms。
- **F2 / M36**：请审类型无关的 `validate_import` 回调，以及对话随书同步的过滤条件。通过 F3 `library_options` 打开的库已经会拒绝删除、改动、重排和改身份；绕过这些选项直接打开 F2 的使用者也要装同一个校验。F1 第七轮补充三条：
  - **被拒的更新不能当成已收**：不存、不推进同步游标。错误说「依赖本机还没有的变更」的，等依赖到了再送一次；按因果顺序送（缺什么补什么）就碰不到这种情况。被拒的更新会挡住同一台设备之后依赖它的所有更新，这一点要在同步状态里看得见，不要静默。
  - **清理没主人的正文**时照 `owns_prose` 就不会删对话；彻底删书时对话随书删（`book.purge` 已经按存储登记的这本书的文档逐篇删）。
  - **校验的代价**：每份传进来的更新都要 `fork` 一份整篇再试导入（2000 条 20 ms）。对话的同步如果热起来，可以先判断这份更新是不是本机全都有了（导入是空操作），是就跳过校验。
- **M27（结构意见，F1 第七轮）**：
  1. **来源**：帮手写对话现在一律 `Origin::User`。助手、思考、工具的记录其实是 Agent 写的，建议用 `agent:<会话>/<轮>`：它会带提交信息留在 Loro 历史里，以后按历史找「谁写了什么」认得出来。作者的记录照旧用 `user`。这不影响撤销，对话不进编辑器的撤销。
  2. **信封字段定死**（`id`、`session`、`turn`、`kind`、`payload`），以后要加的东西放进 `payload`。读取端把记录读成结构体时会丢掉不认识的顶层字段，「同一身份内容是否相同」也就比不到它们；`payload` 是整块保留、整块比较的。真要改信封的话，旧版本会把新记录当成读不懂的跳过（不会再报错），但看不到它。
  3. **大的工具结果**（整章正文、文件内容）会让对话文档变大，而且只追加、永不裁剪，同步和 `.driftingbook` 都跟着大。建议给 `payload` 定个上限，或者把大块内容截短、改成引用书里对象的 id。由 M27 / M28 定。
  4. **每次追加都整篇解析一遍**，用来查重放（2000 条 1.8 ms）。其实运行日志自己知道投到了哪一条；对话到上万条时，可以在持有者那边记住已投的身份，或者只在恢复重放时查。现在不用改。
- **M31**：读取记录或本机运行日志后还原消息；不要维护可独立写入的消息副本。想在界面上提示「这段对话有读不懂或冲突的记录」时，读 `problems()`。
