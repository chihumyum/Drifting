## 1. 大白话

**为什么做。** kernel-v5 让项目有了自己的定义，但能用来新建项目的模板只有写死在代码里的「写书」一份。作者的方向是通用的 Markdown 编辑器，写书只是其中一种项目；别的项目长什么样，要让用户自己攒出来、存下来、拿给别人用。

**做成什么：**

1. **项目模板有一种数据格式。** 用户自己存的、别人给的、社区里的，都是这种格式的一份文件。内置的「写书」留在 App 里，不做成文件（作者已定）；新建项目时它和别的模板走同一条路。
2. **另存。** 在作品主页把当前项目另存成模板：带走项目的定义和骨架，不带写的内容。
3. **我的模板。** 存下来的模板放在书库里，跟着书库同步到自己的其他设备。要改一份模板，打开一个单独的编辑工作区，在里面用平常的界面改，改了就存进模板（2026-11-15 夜里定，第 12 节）。
4. **模板文件。** 一份模板可以导出成一个 `.driftingtemplate` 文件发给别人，对方导入。
5. **社区模板。** 一个公开的仓库是集中存放和治理的地方。新建项目时直接在对话框里逛，选一份就建。
6. **模板里带着写给帮手的话。** 用别人的模板建项目，这些话就成了项目里帮手的规矩。不为它加展示和确认：直接导入、直接选，建好以后可以改（作者已定）。

**作者会看到的不同：**

- 新建项目的对话框里只挑模板：内置的、我的、社区的，右边摆着模板里有什么；建好叫「未命名」，在作品主页上起名。
- 作品主页的「项目模板」一块有一行来源和一个「另存为项目模板」。
- 「全部项目」页的左栏多出「我的模板」，一条一条；悬停卡里编辑、导出、删除；能导入模板文件。

**分两期。** 第一期：模板数据、另存、我的模板、模板文件、新建时选。第二期：社区模板，客户端这边只是读一份目录、取一个文件；投稿和审核都在仓库里做，不需要官方服务，也不需要账号。第二期什么时候做，作者 2026-11-16 定了：新版发布以后（[kernel-v5.md](kernel-v5.md) 第 15 节第 43 条）。

**不做的：**

- 不做升级。模板抄进项目以后两边各走各的（沿用 kernel-v4「模板更新与项目无关」）。模板改了、社区里出了新版、被撤了，都不通知已有的项目。
- 不把模板套到已有的项目上。
- 不单独分享一个条目模板。这页只管整份项目模板。
- App 里不做上传和发布。

## 2. 一份项目模板里有什么

| | 内容 |
| --- | --- |
| 一定带 | 项目定义（写给帮手的项目说明、成书的开关和两个字数目标、左栏的 Tab；成书 2026-11-15 夜里起没有起点）；全部没删的条目模板（模块、字段和它的默认值、键值表的初始行、媒体模块的默认摆法、正文初值、动作、写给帮手的说明）；作者自己建的关系类型；视图的名字和它的泳道 |
| 默认带，另存时可以取消 | **骨架条目**：开着「层级」或「收别处的条目」的条目（两个开关见 kernel-v5 第 16 节）。只带标题、模板、两个开关、「下面」的设置、记号、颜色，以及骨架之间的归属和视图刻度位置 |
| 默认不带，另存时逐条勾选 | **示例内容**：其余的条目，连同它的字段值、键值表、媒体模块摆法、每篇正文当前的文字、归属、在视图里的位置。骨架条目的其他字段值、键值表、媒体模块摆法和正文也算示例内容。视图上的时间钉按视图勾选 |
| 永远不带 | 正文的修改历史；批注；补丁；关系；情节规划的内容；项目设定；Project Memory；帮手对话；写作日；快照点；回收站里的东西；画布上的位置；书名和梗概；账号、设备和书库的任何标识 |
| 第一期不带 | 图片和 PDF（立绘字段、媒体模块里的文件、正文里嵌的文件） |

说明：

- **模板不能是「删掉内容的书文件」。** 书文件（2026-11-14 起后缀是 `.driftingproject`，这页别处写的 `.driftingbook` 都是它）带着每篇文档的完整修改历史，删掉的字也在里面，不能拿来公开发。项目模板是从项目当前的样子读出来的一份纯数据，里面没有任何历史。
- **颜色**指模块配置里 `color_field` 指的那个字段。它决定分类和泳道长什么样，算骨架。
- **模板有自己的名字和描述**，和项目的书名、梗概无关。
- **图片和 PDF 第一期不带**的原因：现在库里的文件必须属于某一本书，模板带文件要先给文件另找一个主人；公开仓库也不适合放大文件。
- kernel-v5 第 2 节说项目模板是「一份项目定义 + 一组条目模板 + 起始的条目 + 起始的视图」。这里多带一样：作者自己建的关系类型。它也是定义，而且它的端点限制指着条目模板。

## 3. 模板里的指向

项目里到处是指向具体东西的 id：Tab 挂在哪个层级、新章节住在哪个文件夹。模板要能用来建任意多个项目，所以：

- **模板里不留真实的条目 id 和视图 id。** 条目和视图在模板里用代号（`e1`、`v1`）。新建项目时每个代号换一个新生成的 id，所有指向它的地方一起换。内置模板里「故事线的新章节住在书稿」现在就是这么做的（建书时把书稿的新 id 填进故事线模板的 `home`），只是写死在代码里。
- **条目模板、模块、字段的 id 原样留着。** 它们是项目内部的名字，不同的项目本来就可以重名（每本书的章模板都叫 `tpl-chapter`），书文件导入时也不改写它们。

另存时每一种指向怎么处理：

| 指向什么 | 出现在哪 | 另存时 |
| --- | --- | --- |
| 条目 | Tab 挂的层级；条目模板和条目的「新条目住在」（`home`） | 目标强制带上骨架，另存时不能取消。目标已经不在（进了回收站、两个开关都关了）就留空；Tab 例外：挂的东西已经不在的 Tab 不带进模板（2026-11-15 起 Tab 没有名字、不能换挂的东西，空挂着没有意义）。原来这一格还有「成书的起点」，2026-11-15 夜里成书没有起点了 |
| 条目 | 视图的泳道 | 泳道条目没带上，这条泳道就不带 |
| 条目 | 归属和主归属；视图里的位置；时间钉绑的条目；字段里的条目引用；正文里的条目链接 | 两头都带上了才留。否则丢掉这一条；正文里的链接变成普通文字 |
| 视图 | Tab 挂的视图 | 没删的视图全部带，指着活视图的总能指到；指着已进最近删除视图的不带（照上一行） |
| 条目模板 | 条目用的模板；默认模板；动作的目标；字段的目标模板；关系类型的端点 | 没删的条目模板全带，id 不变。指着已删模板的留空 |
| 文件 | 图片字段；媒体模块；正文嵌入；正文指向文件的链接 | 第一期图片字段和媒体模块留空，文件嵌入段去掉，指向文件的链接变成普通文字 |

新建项目时不存在「指着的东西没带上」这回事：模板进库之前已经过了校验，每个代号都指得到（第 14 节）。

## 4. 数据形状

**这一节就是项目模板的数据格式。** 用户导出、发给别人、导入，放进社区仓库、从社区取下来，书库里存着的，都是它；写成文件就是第 6 节的 `.driftingtemplate`。

里面有哪几块、哪些带哪些不带（第 2 节）、指向怎么写（第 3 节）、结构封闭、版本和兼容、上限见下；**逐个字段的正式规格与唯一校验器（`dr_model::project_template`）见 [project-template-format.md](project-template-format.md)**（2026-11-15 随格式 5 定稿）。

一份模板就是下面这样一个值（内容只为示意）。它和书目文档里的形状尽量一样：`project` 照 kernel-v5 第 10 节的 `project` 根，`templates` 里每一项照书里的条目模板，只是指向条目和视图的地方换成代号。

```json
{
  "format": "drifting.project-template",
  "formatVersion": 1,
  "madeWith": "",
  "name": "世界观手册",
  "description": "",
  "locale": "zh-Hans",
  "revision": 1,
  "credit": {"author": "示例作者"},
  "project": {
    "agent": {"name": "", "description": "", "instructions": ""},
    "book": {"word_target": 120000, "daily_word_target": 1500},
    "tabs": [{"mount": {"kind": "root"}}, {"mount": {"kind": "entry", "entry": "e1"}}]
  },
  "templates": [],
  "relation_types": [],
  "entries": [
    {"ref": "e1", "parent": null, "title": "书稿", "template": "tpl-…", "level": true,
     "overrides": {}, "mark": null, "fields": {}, "kv": {}, "arrangements": {}, "prose": {}}
  ],
  "memberships": [{"host": "e2", "member": "e5", "primary": true}],
  "views": [{"ref": "v1", "name": "叙事时间线", "lanes": [{"entry": "e2"}], "placements": [], "pins": []}],
  "template_prose": {"tpl-…/mod-…": []}
}
```

- **先后就是数组里的先后。** Tab、条目（按树的先序，兄弟之间就是手动排的先后）、泳道、视图都这样；位置键在新建项目时现生成。
- **`project.book` 没有这个键 = 没有成书**，和 kernel-v5 一样；里面只有两个字数目标，没有起点（2026-11-15 夜里去掉 `root`）。`mount` 的种类照 kernel-v5 第 10 节；以后 Tab 能挂别的东西（kernel-v5 第 15 节第 5 条），这里跟着多一种种类。Tab 没有名字（2026-11-15 起）。
- **正文是段落的列表**：每段的段落属性，加若干段带行内标记的文字；条目链接用代号。它就是读正文时得到的那个段落模型，写回去走正常的正文写入。往返一致由测试钉住。模板正文初值（`template_prose`）和示例条目的正文（`entries[].prose`）用同一种写法。
- **`credit` 整个可以空着。** 里面只有署名一栏。署名不用填：导出时取导出的人的账号显示名，没设名字或没登录就没有（2026-11-15 夜里定，第 6 节）。原来还有一栏主页，作者：「主页，暂时不需要这个东西。以后再说社交。」去掉了；还有一栏「改自」哪份模板（`derivedFrom`），作者在补问里选了整个去掉。
- **`revision`** 是这份模板自己的版本：另存时选「替换已有的一份」就加一。
- **结构是封闭的。** 不认识的键、不认识的模块种类一律拒收，这和书目文档「不认识的字段原样保留」相反：模板要给人看全、给检查程序查全，不能有藏东西的地方。
- **上限**（数字在实现时校一遍，写进校验器）：整份不超过 2 MiB；条目模板不超过 200 个；起始条目不超过 2,000 个；全部写给帮手的文字合计不超过 10 万字。
- **格式版本。** `formatVersion` 是模板格式自己的版本，和书目格式号分开。读到比自己新的版本就拒收并说明。第一期照旧干净改（`next/` 还没发给任何人）；社区上线那一刻起，新版 App 承诺能读所有已经发出去的旧版模板，读的时候升级（作者已定，第 16 节）。这是 `next/` 里第一个承诺向后兼容的格式；模板是没有历史的纯数据，升级比书的格式迁移容易得多。

## 5. 存在哪：我的模板

- **每份模板是书库里的一篇文档**，`project-template:<模板 id>`，不属于任何书。里面三样：`meta`（`v = 1` 和文档 id）；`info`（名字、描述、来源、`revision`、建和改的时间）；`payload`（第 4 节的那个值，连同名字、描述等，当成一整个不透明的值存在 `payload.record`，改就整个换；2026-11-15 起 `info` 不再单独写）。
- **跟着书库同步。** 登录了账号，书库就是这个账号的（每个账号在本机一个独立的书库），模板跟着同步到这个账号的其他设备；没登录就在本机库里。本机库和账号库之间搬模板，和搬书一样靠导出文件再导入。
- **服务端应该不用改。** 同步把文档 id 和种类当不透明的字符串传；本机库的文档表和同步引擎都允许文档不属于任何书。PT1 已补两台设备同步重存与删除传播的回归测试。
- **整个换，不合并。** 两台设备各自重存同一份模板，留下后写的那一份，不会出现一半一半的模板，名字也总是跟着它自己的内容。改名也是整份写回。
- **删除是直接清掉**（带确认），不进回收站；清除记录照现有的同步规则传到别的设备。
- **它不是书的内容。** 不计字数、不搜索、不导出、不进书文件、不进 Markdown 文件夹、不参加任何一本书的写入守卫。客户端里按文档种类分支的地方要过一遍（清单见 kernel-v4 第 8 节「客户端里认文档种类的地方」）。
- **来源**记在 `info` 里：`own`（从自己的项目另存的）或 `file`（从模板文件导入的）。

没有选另外两种做法的原因：做成账号一级的单独接口，要新的服务端契约，而且本地构建用不了；做成磁盘上的一个文件夹，不跟着同步，还多一处「库以外的用户数据」要备份。

## 6. 模板文件

- 扩展名 `.driftingtemplate`。**它就是第 4 节那个值写成的一份 UTF-8 JSON 文本**，键的顺序和缩进固定，同一份模板每次导出逐字节相同。
- 书库里存的、发给别人的、放进社区仓库的、从社区取下来的，是同一种东西。放进仓库以后，审的人能直接读它，改版时能看出改了哪几行。
- 它和书文件是两种东西：

| | `.driftingbook` | `.driftingtemplate` |
| --- | --- | --- |
| 是什么 | 整个项目搬家 | 一份项目模板 |
| 外壳 | 压缩包 | 一份文本 |
| 带内容 | 全部 | 默认不带，勾了的示例才带 |
| 带修改历史 | 带 | 不带 |
| 带文件 | 带 | 第一期不带 |
| 导入的结果 | 书库里多一个项目 | 「我的模板」里多一份模板 |
| 能不能公开发 | 不适合 | 能 |

- **导出**：从「我的模板」里导出一份（悬停卡里的「导出（.driftingtemplate）」）。**不出对话框**，直接弹存文件的窗口，模板存的什么样就导出什么样（作者 2026-11-15 夜里：「导出模板我现在觉得是不是不需要一个包含什么的选择器？模板存的什么样就导出什么样如何？」）。**署名直接用账号名**，没登录就没有署名；没有主页（「导出署名有必要？直接用账号名。主页，暂时不需要这个东西。以后再说社交。」）。原来这里写的是导出时填署名和主页、列出带着的全部东西，作废。补问里作者又定了两处（第 16 节第 25 条）：「账号名」是账号的显示名，没设名字就不写，不用邮箱 @ 前面那段；导出一份别人做的模板，署名也只写导出的人，不提原作者，改没改过都一样。
- **导入**：校验过了就直接进「我的模板」，中间没有确认页。**导入总是新增一份**，模板 id 新生成，不覆盖已有的，即使它就是从这台设备导出去的。导入失败照导入项目失败的说法（作者没提异议）。
- 以后要带图片和 PDF 时，格式升一版，外壳换成压缩包；旧的文本文件照样能读。

## 7. 另存

入口在作品主页「项目模板」一块的块头：「另存为项目模板」。形状是作者 2026-11-15 夜里在原型上选的（<https://claude.ai/artifact/8TAAvwXD8oMRLeWd5Hrnie> 第 6 版第「二」节，kernel-v5 第 15 节第 27 条）。

一个大对话框（作者：「甲」）：

1. **左边「条目」树。** 骨架条目默认勾着，其余默认不勾。**勾一个条目连它住的那几层一起勾**；点掉一层，下面没锁的跟着点掉。被指着的条目（左栏 Tab 挂着的、「新条目住在」指着的）**连它上面几层都锁住**，锁住的行显示一把锁和「谁指着」。（作者：「带上上面几层啊」。这条规则是原型会话补的，作者确认了。PT1 的数据层支持「上层没带、下层挪到最近的上层」，这条规则让那种情况不会从界面出现。）
2. **右边：名字、描述**，先填项目的名字和梗概（「别的都甲」）；一道细线；下面是**带走的定义**：
   - **写给 Agent 三栏能改**，先填着项目现在的话；改的只是存进模板的这一份，项目不变（作者：「另存为项目模板，你的写给Agent部分怎么都不能编辑？」；只改模板是原型会话照常理画的）；
   - 成书（开或关、两个目标）、左栏（Tab 的列表，如「全部 · 书稿 · 人物 · 故事线」）照项目现在的值，只摆出来；
   - 时间钉：每个视图一行，勾了带。
3. **底下：取消、「覆盖…」、「新建模板」。** 没有「存为」那一处（作者：「另存为项目模板，为什么需要「存为」这个地方？不应该是新建或者覆盖吗？」「甲」）。「覆盖…」弹出我的模板挑一份，**挑好就覆盖、不问**（「覆盖前不用问」）；**覆盖时留着那一份原来的名字和描述，只换内容**，id 不变、`revision` 加一（作者：「覆盖：自己定」，原型会话定的：名字框先填的是项目名，拿它覆盖会把模板改名）。
4. 存好以后对话框关上，不弹提示（顺着现成做法，作者没提异议）。
5. **保存**：在书目文档的一个固定版本上读，只读活着的东西，照第 3 节换成代号，过校验器，写进书库。

另存不改项目本身。项目记着的来源（`project.source`）也不变。

**从内置的「写书」得到一份模板文件**，走的就是这条路：用「写书」新建一个项目，在作品主页另存为项目模板，再到「我的模板」里导出。

- 另存读的是项目里的东西，不读 App 的代码，所以「写书」留在代码里不影响它。
- 产品代码不按内置模板的 id 认东西（门禁管着），所以照导出的模板建出来的项目，和直接用内置的建出来的行为一样。
- 这是 PT1 的第一条回归测试（第 15 节）。
- 不建项目、直接把内置的那一份导出来，这页没有做。

## 8. 新建项目

- **只有一条路。** `project.create` 收一份模板值（kernel-v5 第 12 节已定）。内置的「写书」是 App 代码里造出来的一份模板值（kernel-v5 的数据层就是这么做的），我的模板是从书库读出来的，社区的是取下来的；后两种先过读取和校验。三种进了 `project.create` 就没有区别。
- **新建对话框只挑模板，不起名字**（作者 2026-11-15 夜里：「不用在弹窗这里给项目起名字，直接选好了模板，然后直接新建，去工作区了再在项目主页起名之类的。另外，新建项目时最好能看到模板内置了什么结构指令之类的。」）：
  - 左边：内置（写书）、一道线、我的模板（能收，默认展开）、社区（第二期，第 9 节；没配社区目录地址的构建没有这一处）。默认选着「写书」（「别的都甲」）。
  - 右边：模板名、署名、描述，下面「结构」（条目树）、「写给 Agent」、左栏、视图、成书开关。没有「改自」（第 16 节第 26 条）。
  - 点「新建」直接建好，打开新项目的作品主页。**新项目叫「未命名」**（作者：「你定」，原型会话定的：和别处没起名的东西一样，用模板名会冒出一串同名的「写书」）。打开作品主页时**标题已经选中，直接打字就是起名**（作者：「甲」）。
  - **没有自己的模板时照样出对话框**，左边只有「写书」一份，右边看得到它里面有什么（作者在补问里选「甲」，第 16 节第 24 条）。原来写的「只有内置的一份可选时，不出现选择，对话框和现在一样」作废。
- **选社区的模板是直接选。** 点一份，客户端把它的模板文件取下来、校验，再点新建就建好并打开。不需要先把它存进「我的模板」，也不需要账号。取不到社区模板时只说「取不到社区模板」，不加重试（原型会话补的，作者「别的都甲」确认）。
- **写的顺序**和导入一样：先写正文文档（模板正文初值、示例条目的正文），再写书旁边的三篇小文档，最后写书目文档。中途失败，把已经写下的清掉，不留半个项目。
- **新项目记着来源。** `project.source` 在 kernel-v5 的 `{id, version}` 之外多记：`origin`（`builtin` / `own` / `file` / `community`）、模板的名字、署名。只记不用：它用来在作品主页「项目模板」一块显示一行来源。原来还用来在再分享时填「改自」，「改自」去掉了（第 16 节第 26 条）。
- 建好以后，模板和项目各走各的。用户选了社区模板建了项目，这份模板后来怎样，和这个项目无关。

## 9. 社区模板

作者的设想：新建项目时就能逛社区模板，直接选；模板集中存在一个地方；用 GitHub 之类的地方治理。

### 仓库就是那个集中的地方

- **一个公开的仓库。** 每份模板一个文件夹，里面就是它的 `.driftingtemplate` 文件，可以再放一份简介。文件夹的名字是这份模板在社区里的 id。
- **投稿是提一个合并请求（PR）**，加一个文件夹。**改版**是再提一个；**撤下**是删掉文件夹；**举报和讨论**用仓库的议题（issue）。
- **自动检查。** 仓库的 CI 用和 App 同一个校验器查每个文件：结构、上限、每个代号都指得到。校验器要能从命令行单独跑（第 15 节 PT2）。
- **人审。** 维护者读合并请求，重点读写给帮手的那几段话。合并了才算上架。所以社区里的每一份模板，上架前都有人读过。
- **署名**看文件里的署名栏和仓库的提交记录。
- **放进仓库的模板，别人想怎么用就怎么用**（作者已定）。仓库里一句声明，投稿就是同意（第 11 节）。

这样不需要官方服务参与：没有上传接口，没有账号，没有审核后台。仓库、它的 CI 和发布不在这个客户端仓库里。

### App 怎么逛

- **目录。** 每次合并以后，仓库的 CI 生成一份目录 `index.json`：目录格式的版本，和每份模板的 id、`revision`、名字、描述、署名、语言、条目模板数、起始条目数、有没有成书、文件的地址和 sha256、更新时间。
- **目录和模板文件作为静态文件发布到一个固定的地址**，App 只认这一个地址。地址是构建时的配置：官方发布的构建带着，没配的构建没有社区这一处、不发任何请求。官方的地址在官网的域名下，由仓库的 CI 发过去；App 不直接连 GitHub（作者已定）。
- **新建对话框**打开社区这一处时取目录（有缓存；取不到就显示取不到，不影响内置的和我的）。选中一份，取它的文件，sha256 和目录里的对不上就不用，再过校验器。
- **目录里的名字、描述和署名用来逛。** 选中一份时显示的就是这些；不为帮手说明另做一页。
- **客户端不上传任何东西**，也不上报用了哪份模板。发出去的只有两个读请求。
- **契约**是两样带版本的东西：目录格式、模板格式。测试用本机起的静态假服务。

### 不做的

- **App 里不做发布。** 要投稿，就在「我的模板」里导出文件，去仓库提合并请求。不会用 GitHub 的人先不管（作者已定）。
- **没有「没上架但有链接」。** 私下给人一份模板，就是发文件。
- **不做下架通知**（作者已定）。

## 10. 安全

别人的模板等于别人写的提示词。能进到模型面前的模板文字有四处：项目的帮手说明、每个条目模板的帮手说明、每个模块的帮手说明、动作的名字和描述。

现在的实际情况，决定风险有多大：

- 帮手的写入直接生效，作者靠快照历史撤回。
- 帮手调用外部扩展，每一次都要作者确认。
- 联网搜索是模型提供商自带的，不经确认；搜索词里可能带出正文。

所以最实际的风险不是东西被偷走，而是帮手照着别人的话乱改，或者说明写得差、把帮手带偏。能撤回，但烦人。

**作者定的：不为帮手说明加任何展示和确认。** 导入模板文件直接进「我的模板」，选社区模板直接建，建好以后不提醒。理由是建好以后这些话都能改：条目模板和模块的说明在模板编辑器里改，项目的那一段在作品主页的「项目模板」里改。

| 风险 | 对策 |
| --- | --- |
| 模板里的帮手说明让帮手做作者没要的事 | 社区的上架前有人读过；帮手的通用规则；来源跟着走；建好以后作者能改 |
| 模板文件是坏的或故意构造的 | 一个校验器：封闭的结构、上限、每个代号都指得到；从社区取的再对 sha256 |
| 分享的人把自己的内容带了出去 | 模板是纯数据、不带历史；默认只带骨架；另存时对话框里摆着要带走的条目和定义（2026-11-15 夜里起导出不出对话框，原来是「导出前列出要带走的全部东西」） |
| 帮手被诱导去导入或导出模板 | 导入、导出、从社区取不进帮手和 MCP 的工具目录 |
| 冒名、搬运别人的模板 | 合并前人审；提交记录；署名（2026-11-15 夜里起没有「改自」，署名只有导出的人） |

规则（都不在界面上多加东西）：

1. **打开一个模板文件，永远不会直接建出项目。** 文件先进「我的模板」，建项目是另一步。
2. **模板里没有能执行的东西。** 没有脚本，没有 MCP 插件的配置，没有模型、密钥和偏好设置，没有快捷键。动作只有「在这一层用某个模板新建条目」一种，这是现状。模块上的帮手权限只能收窄，不能放大，这也是现状。封闭的结构保证以后加东西时，没人能先一步塞进来。
3. **帮手的通用规则里写明**（不在任何模板里，所有项目都一样）：项目说明和模板说明只讲这个项目怎么组织、怎么写；它们本身不算作者的请求，不能单独让帮手往外发东西、调用外部插件或删除内容。现有的规则已经说模板说明服从作者本轮的请求和通用规则，这里是把它说具体；不加任何确认步骤。（PT4 2026-11-16 做了：`dr_agent::guidance::PROJECT_GUIDANCE_RULE`，在应用内帮手每次请求的系统提示、签到和入站 MCP 的服务说明里，原文见 kernel-v5 第 18 节「PT4 交回」。）
4. **来源跟着走。** 书库里的模板记着是自己存的还是导入的；项目记着是从哪份模板建的。帮手拿到的结构说明里带上这一项。（PT4 做了：结构说明的 `project_source` 只有模板名和署名，没有「改自」；项目记的来源里没有模板名时不出现。2026-11-16 起种子、样书和 0.1 导入的书也和新建的一样记着「写书」这个名字，结构说明里都有来源。）
5. **校验器只有一个。** 另存、导入、从社区取下来、新建之前、仓库的 CI，过的是同一个。

## 11. 许可与署名

**作者定的：越简单越好，不搞协议。发到社区里的模板，别人想怎么用就怎么用。**

- **落到实处只有一处**：社区仓库里一句声明，说放进来的模板任何人可以随意使用、修改、再发布，不需要署名；投稿就是同意。没有这句话，按版权的默认规则，别人只能自己看，不能改了再发，所以这一句省不掉。它用现成的 CC0 文本，那就是这句话的标准写法。
- **App 里和模板文件里没有任何关于许可的东西**：不选、不显示、不检查。
- **私下发的模板文件** App 不管。
- **署名**是文件里可选的一栏，导出时取导出的人的账号显示名，没设名字或没登录就没有；导出别人做的模板也一样，不提原作者（2026-11-15 夜里定，第 16 节第 25 条）。App 在新建时的列表、我的模板的悬停卡和作品主页的来源里显示它。它是礼貌，不是义务。
- **改自。** 原来写的是：从一个来自别人模板的项目另存、再导出时，「改自」自动填上游的名字和署名。作者在补问里选了「改自」整个去掉（第 16 节第 26 条）：格式里没有这一栏，悬停卡、新建对话框里也不显示。
- **内置的「写书」。** 它就是现在新建一本书时 App 自动给的那一整套（kernel-v5 把现在的小说模板改名叫「写书」）：左栏的四个文件夹、四个要素分类、十几个条目模板、一个视图，和写给帮手的那些说明。它是 App 代码里的一段程序，作者定的是留在 App 里，不做成文件，也不默认放进社区仓库。谁想从它改，就用它建一个项目，改好了另存。别人从它改出来的模板拿去分享按什么条件算数，这页不处理；作者以后想把它放进社区，自己建一个项目、另存、导出一份放进去就行。

| `project_template.save` | 从一个项目另存：书、名字、描述、勾了哪些条目和时间钉、新建还是替换哪一份。2026-11-15 夜里加（只加不改，任务书 DW）：多收一份写给 Agent 的话，给了就用它、只进模板；替换时名字和描述可以不给，不给就留着那一份原来的。编辑模板的工作区改了就存，也走它；在工作区里不收名字、描述和写给 Agent，改它们用 `project.update`（2026-11-16） |

| `project_template.update` | 改名字和描述 |
| `project_template.remove` | 删除 |
| `project_template.import` | 校验一个模板文件，过了就存进书库；不过就什么都不写 |
| `project_template.export` | 把一份模板写成文件；署名取导出的人的账号显示名，没设名字或没登录就不写（2026-11-15 夜里改，原来是导出时填署名；没有「改自」） |

帮手和 MCP 的工具目录里只有 `list`、`get`、`save`。`import`、`export` 和从社区取要作者亲手做。读社区目录、取模板文件是客户端模块里的网络调用，不是工作区命令。`edit`、`working_copies`、`update`、`remove` 也不在目录里（PT4，2026-11-16）。帮手的 `save` 存的是当前书，没有 `credit`（署名是导出的人的账号名）；覆盖一份（`replace`，或在工作区里存回它编辑的那一份）之前要在这一轮读过那一份、版本没变，和别的写一样「先读后写」；在工作区里给名字、描述或写给 Agent 直接被拒，错误里说去用 `project.update`。细节见 kernel-v5 第 18 节「PT4 交回」。

## 14. 不变量

| 不变量 | 在哪保证 |
| --- | --- |

## 替作者定的

底层做法，设计会话这样定：

- 模板是从项目当前状态读出来的纯数据，不是剪过的 Loro 文档。
- 条目和视图用代号，新建时换新 id；条目模板、模块、字段的 id 原样留着。
- 模板里的先后用数组的先后，位置键新建时现生成。
- 正文用段落列表存，不用 Loro 快照：快照里能藏历史和别的容器，审的人和检查程序都看不透。
- 模板文件是固定写法的一份文本，不是压缩包：放进仓库能直接读、能看出差别。
- 结构封闭，不认识的东西拒收；一个校验器管所有入口，包括仓库的 CI。
- 书库里一份模板一篇文档，`payload` 整个换；删除直接清掉，不进回收站。
- 导入总是新增一份。
- 骨架条目只带颜色这一个字段；时间钉算内容。
- 社区仓库里那一句声明用现成的 CC0 文本。
- 帮手的通用规则加一条；导入、导出、从社区取不给帮手和 MCP。
- 社区目录的地址是构建时的配置；没配就没有社区这一处。
- 模板文件里没有许可这一栏。
- 上限的几个数字。

2026-11-15 夜里，项目模板界面的原型会话定的（作者说「你定」「自己定」，或照常理画的；作者没逐条确认）：

- 覆盖一份模板时留着它原来的名字和描述，只换内容（「覆盖：自己定」）。
- 新建的项目叫「未命名」（「你定」）。
- 另存对话框里改写给 Agent 的三栏，改的只进模板，项目不变（照常理画的）。

同一天监管会话定的：模板格式去掉 `book.root`（成书没有起点了）和 `credit.homepage`，`credit.author` 导出时取账号名；格式还没发布，直接改，不留兼容。编辑模板的工作区数据上是一种临时项目，怎么标记交给做数据层的那一步（任务书 DW）。
