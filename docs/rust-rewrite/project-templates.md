# 用户自己的项目模板（设计稿）

2026-11-13 起草。**这是设计稿：没有审过，没有实现，没有排期。** 它接着 [kernel-v5.md](kernel-v5.md) 第 2 节「项目定义」和第 15 节第 3 条往下写：把一个项目另存成项目模板、用它新建项目、把它分享给别人。

kernel-v5 的数据层（格式 5）在这页起草时还在实现。本页用到的 `project` 根、「写书」项目模板和 `project.create`，都按 kernel-v5 第 2、10、12 节写；数据层交回后形状有出入的话，以交回的为准，回来改这页。

作者的输入只有三句话，原话在末尾「输入」一节。作者没有答复的问题，本页按建议的做法先写，逐条列在第 16 节；设计会话自己定的底层做法单列在「替作者定的」。

## 1. 大白话

**为什么做。** kernel-v5 让项目有了自己的定义，但能用来新建项目的模板只有编在 App 里的「写书」一份。作者的方向是通用的 Markdown 编辑器，写书只是其中一种项目；别的项目长什么样，要让用户自己攒出来、存下来、拿给别人用。

**做成什么：**

1. **项目模板是一份数据。** 内置的「写书」和用户自己存的是同一种东西，新建项目时走同一条路。
2. **另存。** 在项目主页把当前项目另存成模板：带走项目的定义和骨架，不带写的内容。
3. **我的模板。** 存下来的模板放在书库里，跟着书库同步到自己的其他设备。
4. **模板文件。** 一份模板可以导出成一个 `.driftingtemplate` 文件发给别人，对方导入。
5. **社区模板库。** 官方服务里一个集中存放的地方。新建项目时直接在对话框里逛，选一份就建；自己的模板可以发布上去。
6. **别人的模板先看后用。** 模板里带着别人写给帮手的话，用之前要看到全文。

**作者会看到的不同：**

- 新建项目的对话框里可以选模板：内置的、我的、社区的。
- 项目主页的「项目模板」多一行来源和一个「另存为项目模板」。
- 书架（以后的项目管理页）多出「我的模板」，能改名、删除、导出、发布，能导入模板文件。

**分两期。** 第一期不碰服务端：模板数据、另存、我的模板、模板文件、新建时选。第二期是社区模板库：浏览、直接选、发布、举报和下架，要官方服务那边实现一份新的网络契约。本地构建只有第一期的东西。

**不做的：**

- 不做升级。模板抄进项目以后两边各走各的（沿用 kernel-v4「模板更新与项目无关」）。模板改了、社区里出了新版，都不通知已有的项目。
- 不把模板套到已有的项目上。
- 不单独分享一个条目模板。这页只管整份项目模板。

## 2. 一份项目模板里有什么

| | 内容 |
| --- | --- |
| 一定带 | 项目定义（写给帮手的项目说明、成书的开关、起点和两个字数目标、左栏的 Tab）；全部没删的条目模板（模块、字段和它的默认值、键值表的初始行、正文初值、动作、写给帮手的说明）；作者自己建的关系类型；视图的名字和它的泳道 |
| 默认带，另存时可以取消 | **骨架条目**：开着层级的条目。只带标题、模板、开关、「下面」的设置、记号、颜色 |
| 默认不带，另存时逐条勾选 | **示例内容**：其余的条目，连同它的字段值、键值表、每篇正文当前的文字、归属、在视图里的位置。骨架条目的其他字段值、键值表和正文也算示例内容。视图上的时间钉按视图勾选 |
| 永远不带 | 正文的修改历史；批注；补丁；关系；情节规划的内容；项目设定；Project Memory；帮手对话；写作日；快照点；回收站里的东西；画布上的位置；书名和梗概；账号、设备和书库的任何标识 |
| 第一期不带 | 图片和 PDF（立绘字段、媒体模块里的文件、正文里嵌的文件）。见第 16 节第 9 条 |

说明：

- **模板不能是「删掉内容的书文件」。** `.driftingbook` 带着每篇文档的完整修改历史，删掉的字也在里面，不能拿来公开发。项目模板是从项目当前的样子读出来的一份纯数据，里面没有任何历史。
- **颜色**指模块配置里 `color_field` 指的那个字段。它决定分类和泳道长什么样，算骨架。
- **模板有自己的名字和描述**，和项目的书名、梗概无关。
- kernel-v5 第 2 节说项目模板是「一份项目定义 + 一组条目模板 + 起始的条目 + 起始的视图」。这里多带一样：作者自己建的关系类型。它也是定义，而且它的端点限制指着条目模板。

## 3. 模板里的指向

项目里到处是指向具体东西的 id：成书从哪个条目开始、Tab 挂在哪个层级、新章节住在哪个文件夹。模板要能用来建任意多个项目，所以：

- **模板里不留真实的条目 id 和视图 id。** 条目和视图在模板里用代号（`e1`、`v1`）。新建项目时每个代号换一个新生成的 id，所有指向它的地方一起换。内置模板里「故事线的新章节住在书稿」现在就是这么做的（建书时把书稿的新 id 填进故事线模板的 `home`），只是写死在代码里。
- **条目模板、模块、字段的 id 原样留着。** 它们是项目内部的名字，不同的项目本来就可以重名（每本书的章模板都叫 `tpl-chapter`），书文件导入时也不改写它们。

另存时每一种指向怎么处理：

| 指向什么 | 出现在哪 | 另存时 |
| --- | --- | --- |
| 条目 | 成书的起点；Tab 挂的层级；条目模板和条目的「新条目住在」（`home`） | 目标强制带上骨架，另存时不能取消。目标已经不在（进了回收站、关了层级）就留空，新项目里显示为空并提示重新选（kernel-v5 已有的规则） |
| 条目 | 视图的泳道 | 泳道条目没带上，这条泳道就不带 |
| 条目 | 归属和主归属；视图里的位置；时间钉绑的条目；字段里的条目引用；正文里的条目链接 | 两头都带上了才留。否则丢掉这一条；正文里的链接变成普通文字 |
| 视图 | 成书的起点 | 视图全部带，所以总能指到 |
| 条目模板 | 条目用的模板；默认模板；动作的目标；字段的目标模板；关系类型的端点 | 没删的条目模板全带，id 不变。指着已删模板的留空 |
| 文件 | 图片字段；媒体模块；正文嵌入 | 第一期留空，嵌入处去掉 |

新建项目时不存在「指着的东西没带上」这回事：模板进库之前已经过了校验，每个代号都指得到（第 14 节）。

## 4. 数据形状

一份模板就是下面这样一个值（JSON 只为示意）。它和书目文档里的形状尽量一样：`project` 照 kernel-v5 第 10 节的 `project` 根，`templates` 里每一项照书里的条目模板，只是指向条目的地方换成代号。

```json
{
  "format": "drifting.project-template",
  "formatVersion": 1,
  "name": "世界观手册",
  "description": "",
  "locale": "zh-Hans",
  "credit": {
    "author": "",
    "license": "",
    "homepage": "",
    "derivedFrom": {"name": "", "author": "", "license": ""}
  },
  "project": {
    "agent": {"name": "", "description": "", "instructions": ""},
    "book": {"root": {"kind": "entry", "entry": "e1"}, "word_target": 0, "daily_word_target": 0},
    "tabs": [{"name": "", "mount": {"kind": "entry", "entry": "e1"}}]
  },
  "templates": [],
  "relation_types": [],
  "entries": [
    {"ref": "e1", "parent": null, "title": "", "template": "tpl-…", "level": true,
     "overrides": {}, "mark": null, "fields": {}, "kv": {}, "prose": {}}
  ],
  "memberships": [{"host": "e2", "member": "e5", "primary": true}],
  "views": [{"ref": "v1", "name": "", "lanes": [{"entry": "e2"}], "placements": [], "pins": []}],
  "template_prose": {"tpl-…/mod-…": []}
}
```

- **先后就是数组里的先后。** Tab、条目（按树的先序，兄弟之间就是手动排的先后）、泳道、视图都这样；位置键在新建项目时现生成。
- **`project.book` 没有这个键 = 没有成书**，和 kernel-v5 一样。`mount` 和 `root` 的种类照 kernel-v5 第 10 节；以后 Tab 能挂别的东西（kernel-v5 第 15 节第 5 条），这里跟着多一种种类。
- **正文是段落的列表**：每段的段落属性，加若干段带行内标记的文字；条目链接用代号。它就是读正文时得到的那个段落模型，写回去走正常的正文写入。往返一致由测试钉住。模板正文初值（`template_prose`）和示例条目的正文（`entries[].prose`）用同一种写法。
- **`credit` 整个可以空着。** 自己用的模板不需要署名和许可，分享时才填（第 11 节）。
- **结构是封闭的。** 不认识的键、不认识的模块种类一律拒收，这和书目文档「不认识的字段原样保留」相反：模板要给人看全、给服务端查全，不能有藏东西的地方。
- **上限**（数字在实现时校一遍，写进校验器和网络契约）：整份不超过 2 MiB；条目模板不超过 200 个；起始条目不超过 2,000 个；全部写给帮手的文字合计不超过 10 万字。
- **版本。** `formatVersion` 是模板格式自己的版本，和书目格式号分开。读到比自己新的版本就拒收并说明。旧版本怎么办见第 16 节第 11 条。

## 5. 存在哪：我的模板

- **每份模板是书库里的一篇文档**，`project-template:<模板 id>`，不属于任何书。里面三样：`meta`（`v = 1` 和文档 id）；`info`（名字、描述、来源、署名、建和改的时间）；`payload`（第 4 节的那个值，当成一整个不透明的值存，改就整个换）。
- **跟着书库同步。** 登录了账号，书库就是这个账号的（每个账号在本机一个独立的书库），模板跟着同步到这个账号的其他设备；没登录就在本机库里。本机库和账号库之间搬模板，和搬书一样靠导出文件再导入。
- **服务端应该不用改。** 同步把文档 id 和种类当不透明的字符串传；本机库的文档表和同步引擎都允许文档不属于任何书。这是读代码得出的，没有实测，第一期要补一条两台设备的测试。
- **整个换，不合并。** 两台设备各自重存同一份模板，留下后写的那一份，不会出现一半一半的模板。改名只动 `info`。
- **删除是直接清掉**（带确认），不进回收站；清除记录照现有的同步规则传到别的设备。
- **它不是书的内容。** 不计字数、不搜索、不导出、不进书文件、不进 Markdown 文件夹、不参加任何一本书的写入守卫。客户端里按文档种类分支的地方要过一遍（清单见 kernel-v4 第 8 节「客户端里认文档种类的地方」）。
- **来源**记在 `info` 里：`own`（从自己的项目另存的）或 `file`（从模板文件导入的），加上导入时文件里的署名和许可。

没有选另外两种做法的原因：做成账号一级的单独接口，要新的服务端契约，而且本地构建用不了；做成磁盘上的一个文件夹，不跟着同步，还多一处「库以外的用户数据」要备份。

## 6. 模板文件

- 扩展名 `.driftingtemplate`。外壳和 `.driftingbook` 一样：一个压缩包，里面是 `manifest.json`（格式名、版本、导出它的 App 版本、导出时间、校验和）和 `template.json`（第 4 节的值）。读的时候照书文件已有的做法（大小上限、校验和、清单里不认识的键拒收），另加一条解压后的大小上限。
- 它和书文件是两种东西：

| | `.driftingbook` | `.driftingtemplate` |
| --- | --- | --- |
| 是什么 | 整个项目搬家 | 一份项目模板 |
| 带内容 | 全部 | 默认不带，勾了的示例才带 |
| 带修改历史 | 带 | 不带 |
| 带文件 | 带 | 第一期不带 |
| 导入的结果 | 书库里多一个项目 | 「我的模板」里多一份模板 |
| 能不能公开发 | 不适合 | 能 |

- **导出**：从「我的模板」里导出一份。导出时可以填署名、许可、主页（第 11 节）。
- **导入**：先校验，再出一页模板详情（第 10 节），作者点了才进「我的模板」。**导入总是新增一份**，模板 id 新生成，不覆盖已有的，即使它就是从这台设备导出去的。

## 7. 另存

入口在项目主页的「项目模板」。

1. 作者给模板起名、写描述（可空）。
2. 一棵条目树：骨架条目默认勾着，其余默认不勾；被成书起点、Tab、`home` 指着的条目勾着且不能取消。每个视图一个勾，管它的时间钉带不带。
3. 可以存成新的一份，也可以替换「我的模板」里已有的一份（id 不变，版本加一）。
4. 保存：在书目文档的一个固定版本上读，只读活着的东西，照第 3 节换成代号，过校验器，写进书库。

另存不改项目本身。项目记着的来源（`project.source`）也不变。

对话框长什么样要先出原型。这里只定它有哪些东西，不定文字和排法。

## 8. 新建项目

- **只有一条路。** `project.create` 收一份模板值（kernel-v5 第 12 节已定）。内置的「写书」是编在 App 里的一份模板值，我的模板是从书库读出来的，社区的是下载下来的，三种进了 `project.create` 就没有区别。
- **新建对话框里选模板**，三处来源：内置的、我的模板、社区模板库（第 9 节；本地构建和服务不支持时没有这一处）。只有内置的一份可选时，不出现选择，对话框和现在一样。
- **选社区的模板是直接选。** 点一份，客户端把它的模板文件取下来、校验、显示详情，再点新建就建好并打开。不需要先把它存进「我的模板」。
- **写的顺序**和导入一样：先写正文文档（模板正文初值、示例条目的正文），再写书旁边的三篇小文档，最后写书目文档。中途失败，把已经写下的清掉，不留半个项目。
- **新项目记着来源。** `project.source` 在 kernel-v5 的 `{id, version}` 之外多记：`origin`（`builtin` / `own` / `file` / `hub`）、模板的名字、署名、许可，社区来的再记它在模板库里的编号。只记不用：它用来在项目主页显示一行来源、再分享时填「改自」、以及下架通知（第 9 节）。
- 建好以后，模板和项目各走各的。

## 9. 社区模板库

作者的设想：新建项目时就能逛社区模板，直接选；模板集中存在一个地方。

- **集中的地方是官方服务。** 它是单独运营的服务，源码不在这个仓库。客户端这边只有三样：一份带版本的网络契约、调用它的客户端模块、测试用的本机假服务（和账号、同步的假服务同一个做法）。契约的正文在服务那边写，这里列的是客户端依赖的部分。
- **社区的界面和请求都在 Hosted 开关后面。** 本地构建不发任何模板库的请求，新建对话框里没有社区这一处。服务没有这组路由（404）时当作不支持，同样不出现，不报错。

### 一份模板在库里的状态

| 状态 | 谁能看到 |
| --- | --- |
| 已发布、没上架 | 知道编号的人。编号是猜不出来的，所以它同时就是分享链接 |
| 已上架 | 所有人，在新建对话框里能逛到、搜到 |
| 已下架 | 没有人。发布者自己撤的，或者运营方处理举报后撤的 |

从「已发布」到「已上架」要不要先经过运营方审，见第 16 节第 3 条。这页按先审写。

### 客户端依赖的契约

| 请求 | 谁能调 | 作用 |
| --- | --- | --- |
| `GET /api/templates/v1/items` | 所有人（第 16 节第 4 条） | 已上架模板的列表，分页，可以搜、按语言筛。每项：编号、版本、名字、描述、署名、许可、语言、文件的大小和 sha256、条目模板数和起始条目数、有没有成书、上架时间 |
| `GET /api/templates/v1/items/<编号>` | 所有人 | 一份模板的信息。没上架的凭编号也能取 |
| `GET /api/templates/v1/items/<编号>/package` | 所有人 | 模板文件本身，就是第 6 节的那个文件 |
| `POST /api/templates/v1/items` | 登录的账号 | 发布：传模板文件；返回编号 |
| `PUT /api/templates/v1/items/<编号>` | 发布者 | 换一版（版本加一）、改描述、申请上架 |
| `DELETE /api/templates/v1/items/<编号>` | 发布者 | 撤下 |
| `GET /api/templates/v1/mine` | 登录的账号 | 我发布过的，和各自的状态 |
| `POST /api/templates/v1/items/<编号>/report` | 登录的账号 | 举报 |
| `POST /api/templates/v1/status` | 所有人 | 传一组编号，返回其中已下架的（下架通知，第 16 节第 12 条） |

- **客户端不信服务端给的摘要。** 列表里的名字、描述只用来逛。选中一份以后，详情里显示的结构和写给帮手的文字，一律从取下来的模板文件里现算；文件的 sha256 和列表里的对不上就不用。
- **服务端也要校验。** 发布时服务端用同一份结构定义再查一遍，不合格的不收。这是服务那边的事，写进契约。
- **使用次数**由服务端自己按取文件的次数数，客户端不另外上报。

### 发布

入口在「我的模板」。发布前作者看到的就是别人会看到的那一页详情，加上三样要填的：署名（默认是账号的显示名）、许可（必选，第 11 节）、语言。发布后可以换一版、撤下。换版不影响已经用旧版建好的项目，也不通知任何人。

### 举报和下架

- 详情里有举报入口（要登录）。处理举报在官方服务的运营台，不在客户端。
- **下架通知。** 模板被运营方下架以后，已经用它建的项目收不回来。客户端定期拿本机用过的社区模板编号（项目的来源里记着）去问一次，有被下架的，就在通知中心提示是哪些项目。这会把这些编号发给服务端，做不做见第 16 节第 12 条。

### 链接

每份已发布的模板都有编号，所以「发个链接给别人」不需要另一套东西：链接指向官网上的一页预览，点了在 App 里打开同一页详情。网页在官网那边做，客户端这边只多一个打开链接的入口。排在浏览和发布之后。

## 10. 安全

别人的模板等于别人写的提示词，而帮手的写入直接生效。能进到模型面前的模板文字有四处：项目的帮手说明、每个条目模板的帮手说明、每个模块的帮手说明、动作的名字和描述。

| 风险 | 对策 |
| --- | --- |
| 模板里的帮手说明让帮手做作者没要的事（删改、往外发） | 先看后用；帮手的通用规则；来源跟着走；下架通知 |
| 模板文件是坏的或故意构造的 | 一个校验器：封闭的结构、上限、每个代号都指得到；压缩包的大小和解压上限、校验和 |
| 分享的人把自己的内容带了出去 | 模板是纯数据、不带历史；默认只带骨架；导出和发布前列出要带走的全部东西 |
| 列表里写的和文件里的不一样 | 详情一律从文件里现算 |
| 帮手被诱导去导入或发布模板 | 导入、导出、从社区取、发布不进帮手和 MCP 的工具目录 |
| 冒名、搬运别人的模板 | 署名默认取账号显示名；举报；许可和「改自」字段 |

规则：

1. **先看后用。** 第三方模板（从文件导入的、从社区选的）在进「我的模板」或被用来建项目之前，界面上必须已经有它的详情：名字、署名、许可、结构概览（Tab、条目模板、起始条目、有没有成书），以及上面四处文字的原文。打开一个模板文件或链接，永远不会直接建出项目。帮手文字默认摆出来还是折起来，见第 16 节第 5 条。
2. **模板里没有能执行的东西。** 没有脚本，没有 MCP 插件的配置，没有模型、密钥和偏好设置，没有快捷键。动作只有「在这一层用某个模板新建条目」一种，这是现状。模块上的帮手权限只能收窄，不能放大，这也是现状。封闭的结构保证以后加东西时，没人能先一步塞进来。
3. **帮手的通用规则里写明**（不在任何模板里，所有项目都一样）：项目说明和模板说明只讲这个项目怎么组织、怎么写；它们本身不算作者的请求，不能单独让帮手往外发东西、调用外部插件或删除内容。现有的规则已经说模板说明服从作者本轮的请求和通用规则，这里是把它说具体；不加任何确认步骤。
4. **来源跟着走。** 书库里的模板记着是自己存的还是导入的；项目记着是从哪份模板建的。帮手拿到的结构说明里带上这一项。
5. **校验器只有一个。** 另存、导入、从社区取下来、新建之前，过的是同一个。

## 11. 许可与署名

- 模板里有四个可选的字段：署名、许可、主页（只收 `https` 链接）、改自（上游模板的名字、署名、许可）。
- **App 只展示，不强制。** 许可是发布的人对别人说的话，App 不替他执行。
- 从一个来自第三方模板的项目另存，再导出或发布时，「改自」自动填上游的名字、署名和许可，作者能看到上游的许可再决定。
- 自己用的模板不用填。导出文件时可以填；发布到社区时许可必选。
- 这里有三件事要作者定（第 16 节第 7 条）：内置「写书」模板里的文字按什么许可放出；发布时默认选哪种；社区模板库收哪些许可。第一件的原因：那些文字在 AGPL 的仓库里，用户把从「写书」改出来的模板拿去分享，按什么条件算数现在说不清。

## 12. 界面入口

只定每处有什么，文字和排法出原型时定，不加说明性的文字。

| 在哪 | 有什么 |
| --- | --- |
| 项目主页「项目模板」 | kernel-v5 的 T2 要做的几项之外，加两样：一行来源（从哪份模板建的，有署名带署名）；「另存为项目模板」 |
| 新建项目的对话框 | 选模板：内置的、我的、社区的；选中第三方模板时的详情 |
| 书架（以后的项目管理页） | 「我的模板」：改名、删除、导出成文件、发布和撤下，操作照现有规矩放在悬停卡底部。导入模板文件，和导入书放在一起；把 `.driftingtemplate` 文件拖进窗口也能导入 |

模板的内容不在这几处改。要改一份模板，就用它建一个项目，改好了再另存、替换原来那份。

## 13. 命令

都是书库一级的命令，不属于某一本书。

| 命令 | 作用 |
| --- | --- |
| `project.create` | 不变（kernel-v5）：收一份模板值。多收一个来源，写进 `project.source` |
| `project_template.list`、`project_template.get` | 列出我的模板；读一份 |
| `project_template.save` | 从一个项目另存：书、名字、描述、勾了哪些条目和时间钉、新建还是替换哪一份 |
| `project_template.update` | 改名字和描述 |
| `project_template.remove` | 删除 |
| `project_template.inspect` | 只读：校验一个模板文件或一份取下来的模板，返回详情要用的东西。不写任何东西 |
| `project_template.import` | 把校验过的模板存进书库 |
| `project_template.export` | 把一份模板写成文件，带上署名和许可 |

帮手和 MCP 的工具目录里只有 `list`、`get`、`save`。`import`、`export`、从社区取和发布要作者亲手做。社区那一组不是工作区命令，是客户端模块里的网络调用。

## 14. 不变量

| 不变量 | 在哪保证 |
| --- | --- |
| 模板里没有真实的条目 id、视图 id、文件 id、书 id，没有账号、设备、书库的标识 | 校验器；另存的测试 |
| 模板里每个代号都指得到；每个指向条目模板的 id 都在 `templates` 里 | 校验器 |
| 模板是纯数据，不含任何文档的历史 | 形状本身；另存的测试断言删过的字不出现在模板里 |
| 模板的结构是封闭的，不认识的键和种类拒收 | 校验器 |
| 建项目只经过 `project.create`，内置的、我的、社区的没有各自的路 | 命令层；门禁照旧不许产品代码按内置模板 id 认东西 |
| 导入总是新增一份模板，不覆盖已有的 | 命令层 |
| 新建失败不留半个项目 | 写的顺序和清理，照书文件导入 |
| 模板文档不算任何一本书的内容 | 文档种类的各处分支 |
| 第三方模板进库或被用之前，四处帮手文字已经在界面上 | 界面的测试 |
| 导入、导出、从社区取、发布不在帮手和 MCP 的工具目录里 | 目录的测试 |
| 本地构建不发模板库的请求 | 和账号、同步同一道开关；测试 |

## 15. 任务拆分

都排在 kernel-v5 的数据层之后（开工信号是本地分支指针 `ready/kernel-v5-data-layer`，和 kernel-v5 的 T1 到 T8 一样）。界面的两路还要等 kernel-v5 的 T1、T2 合进 `main`，并且等作者看过原型说迁。

| 路 | 做什么 | 范围 | 等谁 |
| --- | --- | --- | --- |
| PT1 模板值 | 模板值的类型和校验器；从项目提取；内置「写书」改成同一种值、`project.create` 只走这一条路；书库里的模板文档和 `project_template.*` 命令；`project.source` 多记的几项 | `dr-model`、`dr-doc`、`dr-workspace`、`dr-store`、`dr-testkit` | 数据层 |
| PT2 模板文件 | `.driftingtemplate` 的读写和导入导出的入口 | `dr-export`、`dr-view-transfer` | PT1 |
| PT3 界面 | 新建时选模板；我的模板；另存对话框；项目主页的来源一行；模板详情 | `dr-view-shelf`、`dr-view-home` | PT1、T1、T2、原型 |
| PT4 帮手 | 通用规则那一条；结构说明带来源；工具目录只放三条 | `dr-agent`、`dr-agent-tools`、`dr-mcp` | PT1、kernel-v5 的 T7 |
| PT5 社区客户端（第二期） | 契约里客户端依赖的部分；客户端模块和本机假服务；新建对话框里逛和直接选；发布、撤下、举报；下架通知 | `dr-account` 或一个新的服务层 crate、`dr-view-shelf` | PT1 到 PT3、契约定稿、原型 |
| 服务端（第二期，不在这个仓库） | 契约的实现；运营台里的审核和下架；官网上的预览页 | 官方服务、官网 | 契约定稿 |

每一路的回归测试：

- **PT1**：一个项目另存再新建，项目定义、条目模板、关系类型、骨架、视图和原来一致，条目 id 全是新的；成书起点、Tab、`home` 在新项目里指着对应的新条目；没勾的条目不在模板里，指着它的链接变成普通文字；删过的字不出现在模板里；内置「写书」经过同一条路建出来的项目和现在的一样；每条校验规则各有一个被拒的例子；两台设备同步一份模板、各自重存后留下后写的；删除传到另一台。
- **PT2**：文件往返一致；坏的校验和、超大的、带不认识的键的、版本更新的各自被拒，且不写任何东西；同一个文件导入两次得到两份。
- **PT3**：只有内置一份时新建对话框没有选择；选我的模板建出来的项目来源对；另存对话框里被指着的条目不能取消；第三方模板的详情里四处帮手文字都在。
- **PT4**：目录里没有导入、导出和发布；结构说明带来源；通用规则那一条出现在每次请求的系统提示里，清空全部模板说明以后还在。模型照不照做测不了（测试用的是合成的模型流），不为它写假测试。
- **PT5**：对假服务逛、选、建；sha256 对不上的不用；404 时没有社区；本地构建不发请求；发布、换版、撤下；下架通知点名到项目。

原型先出四个界面：新建时选模板和逛社区、模板详情、另存对话框、发布。

## 16. 还要作者定的

每条后面是这页暂时按什么写的。

1. **起始条目带多少。** 暂按：骨架默认带，示例内容逐条勾选。
2. **我的模板存在哪。** 暂按：书库里，跟着书库同步。
3. **社区模板上架前要不要先审。** 暂按：先审后上架；没审的只能凭编号打开。帮手权限大，早期量也小，先审稳妥。另一种是先上架、有举报再处理。
4. **没登录能不能逛社区模板。** 暂按：能逛、能用；发布和举报要登录。
5. **选第三方模板时，写给帮手的文字默认全文摆出来，还是折起来、点开才看。** 暂按：摆出来。这是「直接选」和「先看后用」碰在一起的地方。
6. **用第三方模板建的项目，帮手第一次运行前要不要再提醒一次。** 暂按：不要，选的时候已经看过全文。
7. **许可三件事。** 内置「写书」模板的文字按什么许可放出（建议 CC0）；发布时默认选哪种（建议 CC BY 4.0）；社区模板库收哪些（建议只收 CC0 和 CC BY 4.0）。
8. **要不要第二个内置模板「空白」。** 没有的话，做一份不是写书的模板只能从「写书」删起。这和作者说过的「内置只有写书一个」有出入，暂按没有写。
9. **示例条目里的图片和 PDF 带不带。** 暂按：第一期不带。现在库里的文件必须属于某一本书，模板带文件要先给文件另找一个主人；社区模板库收文件也要另算容量和审核。
10. **扩展名** `.driftingtemplate`。
11. **模板格式的兼容承诺。** 社区上线以后，模板库里会一直有旧版本 App 发布的模板。暂按：第一期照旧干净改（`next/` 还没发给任何人）；社区上线那一刻起，新版 App 承诺能读所有已发布的旧版模板，读的时候升级。模板是没有历史的纯数据，升级比书的格式迁移容易得多。这会是 `next/` 里第一个承诺向后兼容的格式。
12. **下架通知做不做。** 暂按：做。代价是客户端会把本机用过的社区模板编号发给服务端。

## 替作者定的

底层做法，设计会话这样定：

- 模板是从项目当前状态读出来的纯数据，不是剪过的 Loro 文档。
- 条目和视图用代号，新建时换新 id；条目模板、模块、字段的 id 原样留着。
- 模板里的先后用数组的先后，位置键新建时现生成。
- 正文用段落列表存，不用 Loro 快照：快照里能藏历史和别的容器，服务端也没法查。
- 结构封闭，不认识的东西拒收；一个校验器管所有入口。
- 书库里一份模板一篇文档，`payload` 整个换；删除直接清掉，不进回收站。
- 导入总是新增一份。
- 骨架条目只带颜色这一个字段；时间钉算内容。
- 详情从模板文件现算，不信服务端的摘要。
- 帮手的通用规则加一条；导入、导出、从社区取、发布不给帮手和 MCP。
- 社区的编号由服务端发、猜不出来，「没上架但有链接」和「分享链接」是同一回事。
- 上限的几个数字。

## 和 kernel-v5 的关系

没有改 kernel-v5 已经定下的东西，下面几处是往上加：

1. **项目模板多带一样**：作者自己建的关系类型（kernel-v5 第 2 节的定义里没有）。
2. **`project.source` 多几个键**：`origin`、名字、署名、许可、社区编号。kernel-v5 第 10 节只有 `{id, version}`。
3. **多一种文档**：`project-template:<id>`，书库一级。
4. **内置「写书」要是一份能序列化的模板值**，不能只是一个在代码里跑的函数。数据层交回时如果还是函数，由 PT1 改。
5. **Tab 能挂什么**：kernel-v5 第 5 节定的是根或一个层级，能不能挂视图或成书序列还开着（第 15 节第 5 条）。模板的形状两种都装得下，不用等。

## 和输入不一样的地方

- **「直接选」之前多一眼。** 作者说新建时逛社区模板、直接选。这页照做了（不用先存进我的模板，点了就建），但选中以后、点新建之前，界面上要有这份模板写给帮手的全文。多的是一屏内容，不是一步确认。摆出来还是折起来留给作者定（第 16 节第 5 条）。
- **设计会话先前的建议改了。** 先前给作者的方案里，社区是「公开仓库投稿，加运营方审过的目录」，分享链接和开放的画廊往后放。作者要的是集中存储、新建时直接逛，所以改成官方服务里的一个模板库；分享链接成了它的一种状态，不再是单独的一级。
