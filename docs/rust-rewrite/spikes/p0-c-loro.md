# P0-C Loro 数据模型探针：结论

2026-11-07。结构定稿见 [loro-schema.md](../loro-schema.md) v0；代码在 `next/spikes/loro-model/`；测量证据在 [acceptance/p0-c-loro-bench.json](../acceptance/p0-c-loro-bench.json) 和 [acceptance/p0-c-crash-recovery.json](../acceptance/p0-c-crash-recovery.json)。

## 结论（大白话）

1. **能用，而且快。** 100 章 150 万字的重型种子，从 SQLite 冷载入全书 100 章的 Loro 文档约 27 ms，再加上第一次读出每章的文字，一共约 90–170 ms；打开 2 万字的一章不到 1 ms，读出段落 1–3 ms；一次按键「提交 + 写进 SQLite」中位数 0.23 ms（预算 2 ms）。全书 100 章读出来后约 60–90 MB 内存。
2. **计划里有一处假设不成立：书序和叙事序不能用 `LoroMovableList`。** 旧版的书序、叙事序是带间隙的连续坐标（时间线上章节块之间可以空着），幕是这条轴上的实数分界，时间钉也是，章节还可以「没放上叙事轴」。列表只能表达先后，表达不了这些。改成和旧版一样：每章一个数字字段。影响：F1 的书目文档表改了一行；M14 时间线不用变。
3. **段落身份（块 ID）记在每段结尾的换行符上，跟着文字走。** 拆段、并段、跨段删除、撤销都测过。会「撞号」的只有一类情形：两台设备同时在同一段的末尾操作（都按回车，或一边回车、一边把这段和下一段合并）。读的时候第一个保留，修复是确定的、两台设备修出来一样。3000 例随机的三设备编辑全部收敛。
4. **批注锚点用一对光标可行（D4 成立）。** 在锚点前后打字不会扩进去；锚住的字删掉一部分锚点就缩小，全删掉就收成一个点，批注本身还在。有一个限制：**撤销删除不会让批注展开回来**，因为撤销插回来的是新字符。要编辑器自己把锚点带进撤销项（F4 的事）。
5. **Agent 写入选「就地写入」**：在打开的文档上提交，带 `agent:` 来源；作者撤销时撤不掉 Agent 的字。另一种「分叉副本写完再导入」慢约 100 倍（每次 3–5 ms 对 0.02–0.07 ms），还会踩 Loro 的撤销 bug #1228。
6. **富文本撤销的三个已知问题，在我们的用法下：**
   - #1229 会踩到：作者设了标题级别（或链接），另一台设备或 Agent 又改了同一处，作者再撤销，会把对方的值也抹掉。只影响格式，不丢字。绕不开，等上游。
   - #1228、#1245 可以绕开：撤销的「合并间隔」设成 0，不用手动分组，由编辑器自己把同一阵连打的几步一起撤。这一条要 P0-B / F4 照做。
7. **导入、回看历史导致的内存膨胀，被「每章一个文档」挡在了几 MB 以内**（一章约 1–3 MB）。但计划里「回看历史用 `fork_at` 开副本」不对：`fork_at` 会让打开的那份文档自己也展开历史，用完不释放（2 万字的章约 1.6–2.8 MB）。改成从 SQLite 另载一份副本再回看，用完全部还回来。
8. **崩溃安全**：60 次随机杀进程，其中 38 次落在「快照已写、旧更新还没删」的事务中间，恢复后零丢失、和确定性重放逐字一致。

**要作者定的事：没有。** 上面都是技术取舍，监管会话可以直接按 v0 推进。唯一值得知会的是第 6 条：#1229 修好之前，「撤销自己的格式改动会连带抹掉别人对同一处的格式改动」这个毛病会一直在，概率低、只影响格式。

## 每条设计：选了什么、为什么、怎么测的

### 书目文档和正文文档各放什么

- **选了什么**：基本照 F1 的表，修正两处：书序和叙事序改成每章的实数字段；集合（别名、所属故事线）用 mergeable 映射的键，键值列表（字段、设定）用「条目 id → {key, value, order}」。完整的根容器表见 loro-schema.md。
- **为什么**：
  - 顺序见结论第 2 条。旧版 `book-act.ts` 的注释说明了「幕按分界、不按成员」是有意的：拖章过分界自动换幕，删章不用记账，幕可以是空的。只有实数坐标能保住这个语义。
  - 键值列表不用列表：同一个旧库在两台设备各导入一次时，列表会多出一份条目，带 id 的映射不会。
  - 每个实体都用 `ensure_mergeable_map`：同一个实体在两台设备上被写入（比如都从旧库导入）时逐字段合并。
- **怎么测的**：`book_entities_merge_when_created_twice`（两边各写一个字段，合并后两个字段都在，内置关系类型只有一个）；`two_devices_importing_the_same_library_do_not_duplicate`。

### 创世变更（新增的设计）

- **选了什么**：每个文档的第一份变更由一个按文档 id 算出的专用对等方写成，时间戳 0，内容固定（正文：`meta` 加一个带块 ID 的换行；书目：`meta` 加内置关系类型）。
- **为什么**：正文永远要以换行结尾。如果每台设备各自给空文档插一个换行，两台设备同时初始化时会合出两个空段。确定性的创世变更在所有设备上字节相同，Loro 按操作 ID 去重，只剩一个。内置的锁定关系类型同理。
- **怎么测的**：`genesis_is_deterministic_and_concurrent_init_merges`（两台设备各自初始化、各自打字，合并后只有一个段落）。

### 段落身份（块 ID）

- **选了什么**：块 ID 是段尾换行符上的 `bid` 标记。新段落的块 ID 用它那个换行符自己的操作 ID（`"计数@对等方"`），全局唯一，不用随机数；导入的旧 uuid 原样保留。规则：
  - 回车一律在光标处插新换行；
  - 段末回车：块 ID 和属性挪到新换行（它现在结束的是刚写的文字），旧换行给新的空段，拿新 ID；
  - 段首回车：上面的空段拿新 ID；段中回车：前半段拿新 ID；
  - 并段、跨段删除：保留起点那段的块 ID 和属性；删掉的是整段时，后面那段不动。
- **为什么**：
  - 「块 ID 跟着文字走」：引用、补丁、Agent 按块 ID 改段落时，作者在段末按回车不能让 ID 跑到新的空段上去。
  - 「在光标处插换行」是试出来的：最初把段末回车的新换行插在旧换行后面（这样不用挪 ID），属性测试马上发现撤销这次回车会删掉文档最后一个换行，正文就不再以换行结尾了。改成在光标处插以后，创世写的那个换行永远是最后一个字符：没有命令删它，撤销也删不到别的对等方写的字符。
  - 新写的换行把全部段落属性显式写全，读取时只认换行上的属性：见下一条「已知现象」。
- **已知现象**：`ExpandType` 只管本机插入。一台设备给某段设标题、另一台同时在这段开头打字，合并后新打的字可能被段落标记盖住。读取时忽略非换行字符上的段落属性，就不会显示错。
- **怎么测的**：
  - 单元测试：`enter_keeps_block_ids_with_the_text`、`split_carries_heading_only_in_the_middle`、`merging_keeps_the_first_paragraph`、`deleting_whole_paragraphs_keeps_the_next_one`、`undo_of_a_merge_restores_both_ids`、`concurrent_splits_never_duplicate_ids`、`repair_is_deterministic_on_two_peers`。
  - 属性测试 `three_peers_converge`（固定随机种子，数字可复现）：三台设备随机打字、回车、跨段删除、设标题、加链接、加锚点、撤销、Agent 写入，任意顺序同步。3000 例全部收敛。其中：
    - 818 例在合并后有重复块 ID，经确定性修复后全部唯一且各设备一致；
    - 关掉回车以后重复为 0；关掉撤销还有 806 例，关掉删除还有 545 例。重复都出在段末回车挪块 ID 上：两边同时在同一段末尾回车，或一边段末回车、另一边同时把这段和下一段合并，两边各把同一个块 ID 挪到了不同的换行上；
    - 段落标记盖到普通字上的情况出现 3897 次，读取全部正确；
    - 2717 个锚点在各设备上解析结果一致，其中 799 个因文字被删而收成一个点。
  - 随机测试的并发远比真实情况密（三台设备在几十个字的文档上来回改）。真实使用里只有多台设备同时改同一段才会撞号，Agent 用就地写入是串行的。

### 批注锚点

- **选了什么**：一对 Loro 光标（D4）。起点挂在第一个被锚字符上，终点挂在最后一个被锚字符上并解析为「+1」。编码后的两个光标以二进制存在书目文档实体的 `anchor` 字段。全删后收成一个点，存成两个相同的光标。
- **为什么**：起止都挂在被锚的字符上，前后打字不会扩进去，和旧版不扩展的批注一样。
- **怎么测的**：`anchors_exclude_edge_typing_and_collapse_on_delete`、`anchors_survive_merge_and_storage`、`anchor_does_not_come_back_after_undo`（确认撤销后不会展开）、属性测试里所有锚点在各设备上解析结果相同、替换光标解析结果相同、`untouched_anchor_keeps_its_text`（没人删的锚点，无论别处怎么插字，始终锚着原来那几个字）。
- **成本**：活字符上的锚点解析 2–9 µs；锚住的字被删后要回放历史，0.1–0.7 ms（5 万字的构想最慢 1 ms）；Loro 给回的替换光标再解析 1–5 µs。因此替换光标存本机缓存就够，不回写书目文档。

### 人物链接

- **选了什么**：键 `entity:<目标 id>`，值 `{kind, block?, end_block?}`，`ExpandType::None`（按前缀 `entity` 配置，Loro 支持带冒号后缀的键共用前缀配置）。
- **为什么**：一个目标一个键，不同目标可以任意重叠（旧版 `excludes: ''` 也允许重叠）；同一目标相邻的两段会合成一段，和旧版一致。`None` 让前后打字不扩进链接（旧版 `inclusive: false`）。
- **怎么测的**：`entity_links_overlap_and_do_not_expand`（重叠、边缘打字、中间打字、跨段链接不打在换行上、解除链接）。重型种子里 1.5 万处链接、200 处重叠。

### 对等方 ID

- **选了什么**：每（设备，文档）一个随机 ID，存 `loro_peer`；库有换代号，备份恢复、复制库时换代，换代后每个文档重新分配。导入旧库用由文档 id 算出的确定性对等方。
- **为什么**：持久化避免每次启动多一个对等方（版本向量越长，导入越慢，见 Loro #1243）。换代是为了堵住「备份恢复后沿用旧 ID、写出和服务器上同 ID 不同内容的变更」这个查不出来的坑。确定性的导入对等方让同一个旧库在两台设备上导入后不会出现两份正文。
- **怎么测的**：`peers_persist_per_doc_and_rotate_with_the_epoch`；`seed_is_byte_identical_across_runs`（两次独立生成逐字节相同）；`two_devices_importing_the_same_library_do_not_duplicate`。

### Agent 写入

- **两种都试了**：

| | 就地写入 | 分叉副本写完再导入 |
| --- | --- | --- |
| 一次写入（插一段 200 字）耗时，2 万字章 / 5 万字构想 | p50 0.02 / 0.07 ms | p50 3.2 / 5.4 ms |
| 额外内存峰值 | 无 | 1.2 / 1.7 MB |
| 作者撤销会不会撤掉 Agent 的字 | 不会 | 不会 |
| 会不会触发 #1228 | 不会（Agent 的提交立刻被当作远端变更合进撤销栈，作者后面的输入不会和前面的合成一项） | 会（分叉看到了作者的中间状态，作者在合并间隔内又改了一次，导入后撤销留下残字） |
| 提交信息能不能在历史里认出 Agent | 能 | 能 |

- **选了什么**：就地写入。来源和提交信息都是 `agent:<会话>/<轮>`，撤销管理器排除 `agent:` 前缀。来源记在 SQLite，提交信息进 Loro 历史，快照往返后仍在。
- **怎么测的**：`agent_writes_carry_a_durable_message`；撤销用例里的两条「作者打字、Agent 写入、作者打字、作者全部撤销」；属性测试里混入 Agent 写入。

### 表格和素材嵌入

- **选了什么**：U+FFFC 单独成段，打 `embed = <嵌入 id>`；内容在 `embeds[<嵌入 id>]`。表格的行、列是带 `order` 的映射，单元格是 mergeable 的 LoroText。删占位不删条目。
- **为什么**：Loro 文本不能嵌对象。条目留着，撤销删除时嵌入能回来（测过）。两台设备同时建同一个单元格会合成同一段文字（测过）。
- **怎么测的**：`embeds_are_placeholders_with_side_entries`。重型种子 60 篇素材笔记里各有一张表格和一个素材嵌入，另有列表、任务（带待办 id）、代码块、提示框。

### SQLite 存储

- **选了什么**：WAL、`synchronous=NORMAL`；每次提交追加一行更新；压缩时在同一个事务里写快照、删被覆盖的更新；载入时快照加之后的更新一次 `import_batch`。DDL 见 loro-schema.md。
- **怎么测的**：
  - `store_round_trip_with_compaction`；
  - `p0c-crash`：子进程不停编辑、每 25 次压缩一次，压缩事务里故意停 20 ms；父进程在随机时刻 `SIGKILL`，重开后与「第 0 到第 k 次编辑」的确定性重放逐字比对，并检查子进程报告过已落盘的编辑一个不少。60 次杀进程（38 次在压缩事务中间）：零丢失，零不一致，块 ID 全部唯一。崩溃后重开（打开库、SQLite 回放 WAL、载入文档）p50 13.5 ms，最慢 29 ms。

**对 F4 的提示**：冷文档第一次被读取时，Loro 会把整章状态解码出来，耗时和读多少字无关（每章约 1–2 ms）。所以全书模式里屏幕外的章节应该先不碰，段落高度用派生索引（F2 的大纲 / 字数索引）估算，章节进入视野时再解码。100 章全部解码约 65–140 ms，接近探针档「打开全书 ≤ 200 ms」的一半预算，一次全解码不可取。

## 已知问题实测

### 富文本撤销（Loro 1.17.1）

在我们的用法下复现（`undo_cases.rs`，结果也在 JSON 证据里）：

| 问题 | 情形 | 结果 |
| --- | --- | --- |
| #1229 | 作者设 H1，另一台设备改成 H2，作者撤销 | 错：变回正文，H2 也没了 |
| #1229 | 同上，但改成 H2 的是就地写入的 Agent | 错：同上 |
| #1229 | 作者设链接，另一台设备改链接地址，作者撤销 | 错：链接没了 |
| #1229 | 作者加粗，另一台设备同一段改斜体，作者撤销 | 对：斜体留着（不同的键不受影响） |
| #1245 | 手动分组包住两次退格，中间远端改了别的映射 | 错：`abcdef` 撤销成 `abcdfe` |
| #1245 | 用合并间隔（不用手动分组），中间有远端或 Agent 的改动 | 对：远端改动把撤销项切成两项，撤两次复原 |
| #1228 | 手动分组：打 `x` 已同步，改成 `y`，远端有依赖它的改动，撤销 | 错：留下 `x` |
| #1228 | 同上但用合并间隔（500 ms 级） | **错：留下 `x`**（用合并间隔也会踩） |
| #1228 | 同上，合并间隔 0，编辑器自己把这一阵的两项一起撤 | 对 |
| #1228 | 分叉的 Agent 写入在作者重打之后才导入，合并间隔内 | 错：留下 `x` |
| #1245 | 合并间隔 0 + 编辑器自己合并，两次退格中间有远端改动 | 对 |

**结论**：编辑器把 Loro 撤销的合并间隔设成 0，不用 `group_start` / `group_end`，自己用撤销项的时间戳决定一次撤销弹出几项。这样 #1228、#1245 都绕开了。#1229 绕不开，只影响格式。测试 `undo_cases_in_our_usage` 把这几个已知的错误钉住：哪天升级 Loro 修好了，测试会失败，提醒改文档。

### 导入和回看历史的内存膨胀

2 万字章（模拟打字 / 反复改写）：

| 操作 | 模拟打字的章 | 反复改写的章 |

## 怎么复现

```bash
cd next
cargo test -p loro-model-spike
P0C_PROP_CASES=3000 cargo test --release -p loro-model-spike --test convergence -- --nocapture
cargo run --release -p loro-model-spike --bin p0c-bench
cargo run --release -p loro-model-spike --bin p0c-crash -- run --kills 60
```

- `p0c-bench` 写 `docs/rust-rewrite/acceptance/p0-c-loro-bench.json`，`p0c-crash` 写 `p0-c-crash-recovery.json`。
- 两份证据都带源码指纹；`--check` 只校验指纹和形状，不校验耗时。
