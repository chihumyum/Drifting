# P0-B 编辑器探针：结论

2026-11-07。代码在 `next/spikes/prose-spike`，测量证据在 `docs/rust-rewrite/acceptance/p0-b-headless.json` 和 `p0-b-window.json`。

## 一句话

**能过关，建议继续。** 在钉住的 GPUI v1.27 上自己写中文长文编辑器，全书性能和写入远低于预算；探针档有三项差一点（按键上屏、组字上屏各差不到 1 ms，空闲 CPU 在 1% 上下），差的部分都出在 GPUI 的刷新节奏上，编辑器自己的那份很小，补救办法也很小。路上踩到的 GPUI 短板都在编辑器这一层绕过去了，不用 fork GPUI。真输入法没能自动测，留了一份手测清单。

## 大白话

**写字快不快。** 编辑器处理一次按键约 0.1 ms，写进 Loro 再追加进 SQLite 约 0.03 ms，都远低于预算。字从按键到出现在屏幕上，平均约 13 ms、最慢约 17 ms（p95 16.6 ms，预算 16 ms）。这段时间几乎全花在「等 GPUI 刷新」上：GPUI 收到按键后要等下一次屏幕刷新才画，画好还要再等一次刷新才显示，在 120 Hz 屏上就是 1 到 2 个刷新周期（8.3–16.7 ms），所以 p95 正好卡在 16 ms 附近。编辑器自己那份不到 2 ms。试了一个「改完立刻画」的办法，p95 降到 15.6 ms 以内，但还要用更准的仪器确认（见下）。

**整本书顺不顺。** 100 章、150 万字：打开约 47 ms，从目录跳到最后一章约 13–15 ms，从头一路滚到尾每一帧的活儿都在 2.5 ms 以内，滚动基本稳在 120 帧，滚完整本书进程只占约 260 MB。

**排版。** 比例字体、H1/H2/H3 各自的字号、段距都按现在 Drifting 的参数排。中文断行一开始不对：「，」「。」会跑到行首。原因是计划里以为 GPUI 已经用上了 ICU 的断行规则，实际钉住的 v1.27 里还没有。现在改成编辑器自己断行：GPUI 只负责把一段字排成字形、把单个字形画出来，哪里换行、标点能不能放行首、标点悬挂都由编辑器决定。这样做以后也方便加两端对齐。

**拼音组字。** 组字过程中的拼音只显示、不写进 Loro；确认上屏时才一次写入，撤销一次正好去掉整个词。选中文字后打拼音，被替换的文字要等确认后才删。组字时失焦，编辑器自己清掉，也通知系统输入法丢弃。组字时 Agent 或远端改了同一章，组字的位置会跟着挪。这些都有自动测试。输入法问「候选窗放在哪」时，编辑器 0.1–0.3 ms 就能答，候选窗不用等编辑器的下一帧。

**Agent 写入不进作者的撤销。** 撤销按来源前缀 `agent:` 排除，有测试证明：作者撤销只撤自己写的，Agent 写的留着。撤销和回车的写法已经照 P0-C 定下的 [loro-schema v0](../loro-schema.md) 改过。

**踩到的坑，都已绕过：**

1. GPUI 要开 `font-kit` 特性才画字，不开时一个字都不出、也不报错（只在日志里一句）。（main 上已经在工作区开了。）
2. 断行不守中文标点禁则（见上）。
3. GPUI 的虚拟列表不能给屏幕外的段落填估算高度，而且第一帧和窗口变宽时会把高度全清掉。所以滚动条和按像素跳转用编辑器自己的高度表（估算误差约 1%），滚动定位仍交给 GPUI。
4. 光标每闪一次会把整屏段落重画一遍。现在光标单独一层，正文做成缓存视图，闪一次只画一条 2 像素的竖线。
5. GPUI 默认把「不在最前面的窗口」限制到 30 帧。作者打字时窗口在最前面，不受影响；测量时要关掉这个限制，不然量出来的是限制本身。
6. GPUI 没有「让系统输入法丢弃组字」的接口。现在由程序这一层直接调用系统的 `discardMarkedText`，十来行。

**要作者定或手测的**（2026-11-07 作者答复「都按照你的建议来」，已定，见 [progress.md](../progress.md)：上屏采用「改完立刻画」但先量准；空闲 CPU 探针档接受、发布档前给 GPUI 打补丁；失焦保持清掉；真输入法由作者手测）：

- **真输入法手测**（最重要）：清单见下面「输入法」一节，每项写了怎么测、怎样算过。
- **按键上屏 16 ms 这条线怎么处理**，三选一：
  - 接受「1 到 2 个刷新周期」（120 Hz 屏上 p95 约 16.6 ms，比旧版的 29–32 ms 快一倍）；
  - 采用「改完立刻画」（已做出原型，p95 ≤ 15.6 ms），先用 Instruments 或高速相机确认真实上屏时间；
  - 给 GPUI 打补丁，让它收到输入就画（发布档 8.3 ms 迟早要做这件事）。
  探针的建议：第二条，F4 接手时先量准。
- **空闲 CPU**：编辑器开着不动时 0.9–1.3%，预算 1%。其中约 1% 是 GPUI 自己的：窗口开着时它每秒醒 120 次等刷新，不管有没有事做（光标闪烁只占约 0.1–0.2%）。要降到接近 0（发布档），需要给 GPUI 打补丁，让它没事时停掉刷新时钟。成本估计见下文，可以提给上游。
- **失焦时的组字**：现在按计划「清掉」，即没确认的拼音直接丢弃。macOS 原生程序多半是把拼音字母原样上屏。要换成原样上屏，改一行。

## 探针档对照

机器：M3 Pro（12 核，36 GB），macOS 27.0.1，窗口放在 120 Hz 内建屏上，release 构建。数字取自本次提交里的证据文件。

| 项 | 预算 | 结果 | 过 |
| --- | ---: | ---: | :---: |
| 按键上屏 p95 | ≤ 16 ms | 16.6 ms（GPUI 默认节奏）；「改完立刻画」≤ 15.6 ms | 差 0.6 ms |
| 单次按键的写入（中位数） | ≤ 2 ms | 0.025 ms（Loro 0.012 + SQLite 0.012） | ✓ |
| 打字时的 CPU（每秒 8 字，60 s） | ≤ 15% | 2.7% | ✓ |
| 不操作时的 CPU（光标闪烁） | ≤ 1% | 全书 1.28% / 单章 0.88%；不聚焦、光标不闪 1.10% | 贴线 |
| 打开 2 万字章节（中位数） | ≤ 80 ms | 12.9 ms | ✓ |
| 打开全书（中位数） | ≤ 200 ms | 46.6 ms | ✓ |
| 全书快速滚动，每帧 p95 | ≤ 16.7 ms | 工作 2.4 ms，帧间隔 9.4 ms | ✓ |
| 跳到末章（最差一次） | ≤ 150 ms | 15.4 ms | ✓ |
| 滚完全书后的内存 | ≤ 800 MB | 258 MB | ✓ |
| 组字中更新候选窗 | ≤ 16 ms | 候选窗位置查询 p95 0.25 ms；组字文字上屏 p95 16.7 ms | 候选窗 ✓，文字差 0.7 ms |

说明：

- 「按键上屏」和「组字文字上屏」的结构下限是一到两个刷新周期：GPUI 收到输入后等下一拍才画，画好的帧下一拍才显示。120 Hz 屏上就是 8.3–16.7 ms（实测最小 8.4、最大 17.0），60 Hz 外接屏上会翻倍。旧版同一项是 29–32 ms。
- 打字测量把按键时刻均匀错开在一个刷新周期里。最初按固定的每 125 ms 一键打，125 ms 正好是 15 个刷新周期，每一键都落在同一个相位上，量出来的分布是假的（全挤在 12.4 ms），已改掉。
- 「立即画」：每次编辑后对 GPUI 的视图发 `setNeedsDisplay:`，Core Animation 会在这一轮事件处理完时回调 GPUI 的 `displayLayer:`，GPUI 当场画一帧。帧在按键后约 2 ms 就画好了（默认约 6 ms），上屏 p95 ≤ 15.6 ms、平均 ≤ 10.6 ms。但 GPUI 在这条路上会停掉再重启刷新时钟，测量探头记下的「下一拍」可能晚于真实上屏，所以这只是上限；早先一次测量里它还出现过几十毫秒的长尾。默认不开，证据里作为对照记录。
- 空闲 CPU 每次测都在 0.7–1.3% 之间晃，30 秒一个窗口。

## 架构：gpui-prose 的起点

只依赖 `gpui` 和 `loro`（`cargo check -p prose-spike --lib --no-default-features` 证明）。

### 数据（给 P0-C 对照）

探针实际用的结构，落在 [loro-schema v0](../loro-schema.md) 里面（只用了 `body` 和 `heading`，没写块 ID `bid`）：

- 每篇正文一个 `LoroDoc`，根容器 `body` 是一个扁平的 `LoroText`。
- 段落以 `\n` 结尾，正文永远以 `\n` 结尾，所以每段都拥有结束它的那个换行符。最后一个换行符后面那个空位置不显示成段落。
- 段落类型是打在换行符这一个字符上的标记 `heading`，值 1/2/3，没有就是正文；`ExpandType::None`，在换行符旁边打字不会继承它。
- 回车：新换行符一律插在光标处（v0 的规则；插在旧换行符后面会让撤销删掉文档最后一个换行符）。段中拆段，标题拆开后两半都是标题；段尾回车，新换行符结束刚写的文字、带上标题，旧换行符结束新的空段、改成正文；段首回车，上面多出来的空段是正文。v0 还要求段尾回车时把块 ID 挪到新换行符上，探针没有块 ID，F4 接进来时补。
- 退格并段：删掉前一段的换行符，并把前一段的类型补到剩下那个换行符上；前一段是空段时保留后一段的类型（照 Quill，和 v0 的并段规则一致）。
- 位置一律按 Unicode 标量计（Loro 原生 Rust 的单位）；给输入法时换成 UTF-16，给排版时换成 UTF-8 字节。
- 编辑器用一份「段落镜像」（每段的文字、类型、长度、版本号）来排版。镜像只靠 Loro 的事件更新：自己打字、撤销重做、导入远端更新走同一条路。有一个随机测试：随机编辑、撤销、重做、远端导入 120 步 × 24 个种子，每一步都和重新从 Loro 读出来的结果比对。

### 撤销

- 每篇正文一个 `UndoManager`，排除来源前缀 `agent:`（以及建文档时的 `seed`）。
- 按 v0 的约束，Loro 的合并间隔设为 0（Loro 自己合并会踩 #1228、#1245），每次提交在 Loro 里是单独一项；文档层自己把同一阵的几项记成作者的一步，撤销一次连续弹出这几项。
- 「同一阵」= 从这一步第一次编辑起 500 ms 内，和 Loro 原来的语义一样：一直打字时每 500 ms 切一步。回车、输入法确认、粘贴、设标题强制新起一步。
- 顺带记下 Loro 自己的两个行为：它的合并间隔也是从一步的第一次编辑算起；`record_new_checkpoint` 不会把合并中的一步切开。
- 全书模式里，一个跨章的栈记住每一步落在哪一章，撤销时按顺序找回去。
- 没做：撤销删除时把批注锚点带回来（v0 说撤销插回来的是新字符，锚点不会自己展开，要编辑器把锚点放进撤销项）。探针没有批注，归 F4。

### 组字

- 组字状态（锚点、被替换的长度、拼音、输入法给的选区）只在编辑器里。输入法看到的「文本」是这一章的正文、在锚点处拼上组字中的文字，按 UTF-16 计。
- `insertText:` 或 `unmarkText` 时，一次提交写入 Loro（替换选区也在这一次里），所以撤销一次去掉整个词。
- 组字中按 ⌘Z：忽略（组字属于输入法）。拼音删光：取消，正文原样不动。
- 失焦：清掉组字并调用系统的 `discardMarkedText`。
- 别人的改动（Agent、同步）会挪动组字的锚点和选区。

### 排版与绘制

- `element.rs` 的 `ProseLayout`：整段交给 GPUI 的 `layout_line` 排成一行字形（GPUI 按文字、字体、字号逐帧缓存），编辑器按中文禁则切成行，再用 `paint_glyph` 逐个画字形，屏幕外的行跳过。
- 禁则：「，。、；：？！」等点号和后半引号、括号不放行首，前半引号、括号不放行末，「——」「……」不拆开，拉丁单词和数字不拆开；行末溢出的点号悬挂在行外。
- 一段只用一种字号（标题和正文分属不同段落），所以不需要一行里混排不同字号的行排版器。

### 虚拟化

- 列表项是：每章一个标题项，加上每段一个段落项。全书约 1 万项。
- Loro 事件告诉编辑器哪几段变了：段数不变就让 GPUI 重新量这一项，段数变了就对列表做相应的增删。
- 编辑器自己维护一份高度表：屏幕外段落的高度在后台线程按字宽估算（全书一遍约 3 ms，误差约 1%），量过的段落换成真实高度。滚动条、按像素滚动都用这份表。

### 渲染

- 正文是一个缓存视图，光标是盖在上面的另一个视图，各自通知各自。
- 输入法接口（`EntityInputHandler`）挂在正文视图上，缓存重放时 GPUI 会连同它一起复用。

### 平台钩子

`PlatformHooks` 有两个方法，由程序这一层实现：`discard_marked_text`（macOS 上调 `[NSTextInputContext discardMarkedText]`）和可选的 `present_now`（上面说的「立即画」实验）。

## 输入法

### 自动测过的

- GPUI 测试平台上，按 macOS 的调用顺序驱动 `setMarkedText:` / `insertText:` / `unmarkText`：组字不进 Loro、确认一次写入、一次撤销、替换选区、拼音删光、失焦清理、组字中撤销、组字时别人改动、含 emoji 的 UTF-16 换算。
- 真实窗口里，进程内模拟 40 个词的组字：每个词组字期间 Loro 的长度不变，确认后正好多两个字。

### 真机试了，没测成

- 当前在用的是豆包输入法。用后台控制在探针窗口里打 `nihao`，字母直接上屏，没有进入组字。
- 原因：系统输入法只给最前面的程序组字，后台控制不会让探针变成最前面的程序。要真测，得接管整个屏幕，这超出了这次约定的授权方式，所以跳过。
- 顺带确认了：后台发来的按键确实走 `insertText:` 进了编辑器，按键路径是通的。

### GPUI 已知的输入法坑，对这个编辑器的影响

- **判断「当前是不是中文输入法」会被骗**（#59882，#63405 没合）：GPUI 只在判断为输入法时才先把可打印键交给输入法，否则先查快捷键。编辑器不绑定任何单个可打印键，没匹配到快捷键的键照样会交给输入法，所以这个误判对正文编辑器没有影响。快捷键只用 ⌘ 组合和方向、回车、退格这类不可打印键。
- **失焦时残留组字**：编辑器失焦时自己清掉，并调用 `discardMarkedText`。
- **Windows**：GPUI 走的是 IMM32，丢弃组字要用 `ImmNotifyIME(…, NI_COMPOSITIONSTR, CPS_CANCEL, 0)`，还没写。

### 待作者手测

准备：

```bash
cd next
cargo run --release -p prose-spike -- chapter          # 一章 2 万字，含一段 5000 字的长段落
cargo run --release -p prose-spike                     # 全书 100 章，左边是目录
PROSE_SPIKE_IME_LOG=1 cargo run --release -p prose-spike -- chapter   # 终端里打印每一次输入法调用
```

窗口底部一行显示光标位置、选区，以及「Loro 正文 N 个字符」。组字时会显示「组字中「…」（未写入 Loro）」，这时 N 不应该变。

每种输入法（macOS：系统拼音、系统注音、豆包、微信输入法、搜狗、百度、系统日语；Windows 等编辑器能在 Windows 上跑再测）都过一遍：

| # | 情形 | 怎么测 | 怎样算过 |
| --- | --- | --- | --- |
| 1 | 章末组字 | ⌘↓ 到章末，打「nihao」选第一个词 | 词出现在章末；N 正好多 2；候选窗贴着光标 |
| 2 | 段首组字 | 点一段的开头再打 | 同上；词在段首 |
| 3 | 长段落中间组字 | 在 5000 字那段（第 1 章中间）的中部点一下再打 | 同上；打字不卡 |
| 4 | 替换选区 | ⇧→ 选几个字，打拼音，看到组字时原文字还在、被盖住；确认 | 确认后原文字被替换；⌘Z 一次恢复原文字 |
| 5 | 组字时失焦 | 组字到一半，点左边目录跳到别的章；或 ⌘Tab 切到别的程序再切回 | 编辑器里不残留拼音；回来后再打字正常组字，不会接着旧拼音 |

| 7 | 撤销整词 | 连续确认几个词后按 ⌘Z | 每次撤掉一个完整的词（同一 500 ms 内确认的会合成一步），不会只撤半个词 |
| 8 | 全书模式组字 | 全书模式里在任意一章组字，组字时用触控板滚动 | 候选窗跟着文字走或保持在文字附近；滚回来组字还在 |
| 9 | 标点 | 中文标点（，。“”《》……——） | 一键一个标点，不重复不丢；「……」「——」整体出现 |
| 10 | 快速连打 | 连续快速打一整句再一次确认 | 不丢字、不重复 |
