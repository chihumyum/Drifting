## 状态怎么读

「状态」一列只用四种说法：

| 状态 | 意思 |
| --- | --- |
| **已验收** | 功能在 v3 上，自动测试全过，并且在真窗口里（调试桥驱动真实的 App，放在副屏）走过主要流程。验的是功能和数据对不对，**不含**样式、流畅度和重型书性能：那些按作者 2026-11-10 的决定暂缓，没测的不算通过 |
| **只在合成环境验过** | 自动测试和真窗口流程都过了，但对面是本机起的假服务、合成的模型流或模拟的系统回调。缺哪一种真实条件写在说明里 |
| **暂缓** | 作者决定现在不做，写明等什么 |
| **没做** | 没有实现 |

带 † 的「已验收」：切换时那一轮真窗口验收（15 条流程：搜索、素材、模板、Agent、链接、排空、释放、结构、归属、历史、主页、时间线、接线、剪贴板、切换）没有单独点到这个模块，证据是自动测试（含挂载真实视图的 GPUI 测试）和切换前的真窗口记录。

每个模块更细的缺口，以它结论文档里的「待协调」为准。

- **自动快照点的「全书条目指纹」是条目数的平方：已修（2026-11-12）。** 现在一次遍历读出全书每个条目的指纹（`BookViewV3::entry_change_states`）。同一轮里量，重型种子的新书目（633 个条目）从 6.7 秒到 18 毫秒，三年后的书目（1,197 个）从 28.7 秒到 31 毫秒。顺带量出并修掉了退出时的最后一遍（`capture_on_close`）：重型书什么都没变的一次退出原来要两三分钟（每个条目各调一次命令，命令里还有一个平方），现在整本书比对一次、只对有事可做的条目调命令，0.11 秒；每个条目都还没有快照点的第一次退出从 81 秒到 6.8 秒，仍然是每个条目一次命令，没有再动。[m09](modules/m09-history.md)、[spikes/history-aging.md 的「修复之后」](spikes/history-aging.md#修复之后2026-11-12)
- **条目的「内容」里含兄弟条目的有序列表：已修（2026-11-12）。** 一个条目变没变现在只看它自己的元数据、名下的记录、父级和它自己的位置键；别的条目新建、删除、挪动不再让同级每个兄弟各存一个快照点。同样的三年模型重量：快照点从 71,508 个降到 12,934 个（被连带的 58,574 个没有了），书目快照从 26.2 MB 降到 7.79 MB，从快照载入从 37 毫秒降到 11 毫秒（旧规则在同一轮重跑作对照）。剩下的 7.79 MB 里快照点清单仍占 4.42 MB（不存快照点是 3.37 MB、载入 5 毫秒），下面第四条要不要挪就看这组数。旧算法存下的快照点照样能预览、恢复和导入（校验时新旧两种指纹都认，清单不改写）；这样的条目下一次自动捕获会多存一个新指纹的点。旧版本的构建不认新指纹的点（两台设备版本不一致时，旧的那台预览不了新的那台存的点），这是有意接受的。
- **写作日每分钟往书目文档提交一次：已挪出（2026-11-13）。** 写作日现在存在每本书旁边的 `stats:<书>` 里，记一次写作日不再推动书目文档的版本、不发 `Book` 事件；11-12 临时加的 `BookChanged.touched` 分类随之删掉。三年的书上，另一台设备收到一次写作日从 77.5 ms（含整份书目的导入校验）降到 0.06 ms。上传批数略增（每个写作日 79.9 → 86.2，三篇文档各传各的），其中书目文档只有 16.5 批。写作日 60 秒落盘的间隔没动。[kernel-v4.md](kernel-v4.md) 第 8 节
  - 还剩的代价：每次写作日仍是书目文档的一次提交、一批上传，另一台设备每收到一批仍要校验整份书目（三年的书约 78 毫秒）；书目的版本照旧被推进，按整篇版本做的缓存和守卫（链接名字的按书缓存、带整本版本的受守卫调用）照旧看得见这些提交。
  - 把写作日挪进每本书一份的小文档，设计已写完、**暂缓**：分支 `chihumyum/next-side-docs`（提交 `16ebbd34d`，`foundations/f2-side-docs.md`，没合进 `main`）。读代码发现它并不能让书架少开书目、也不减少上传批数，剩下的好处主要是书目体积和远端校验，代价却是永久的（新旧并读、书文件升版本）。等条目模型定形、书目结构还要不要动定了以后一起决定，格式只改一次。
- **快照点清单存在书目文档里：已挪出（2026-11-13）。** 清单现在存在 `checkpoints:<书>` 里，存点不再写书目文档。三年的书目快照从 7.79 MB 降到 3.07 MB（清单文档自己 4.31 MB、写作日文档 0.20 MB），从快照载入 10.9 → 4.4 ms。修剪仍然只删键，删掉的清单留在清单文档的历史里；它自己会不会长得太大，以后再量。11-12 为旧指纹留的兼容随格式 4 删掉了（格式 4 的库里没有旧指纹的点）。
  - 还剩的代价：书目的体积和载入（7.79 MB、11 毫秒，挪走是约 3.1 MB、约 5 毫秒），每次存点一批上传。
  - 外移的设计和上一条在同一份文档里，同样暂缓。
- **书目的导入校验每次整份导出再导入**（`dr-workspace` 的 `library_options`）：新书目一次 13 ms，三年后 268 ms，在书目的存储线程上。写入守卫那一路查过，判断方法没改：试过的五种做法里没有既安全又不带来新代价的（[f3-write-guards.md](foundations/f3-write-guards.md) 的「导入校验」）。代价跟着书目文档的大小走，等书目瘦身以后再量；还不够，再做「把校验用的拷贝留着」这个缓存。
- **导入校验补了一个漏洞，留下一个已接受的后果。** 改 `meta.v` 的更新先到、它依赖的更新后到时，原来能绕过校验把书存成非 v3、重开后打不开；现在校验用的拷贝也并入还在等依赖的更新，三种到达顺序都进不来。后果：被拒以后那份挂起的更新还留在内存里，带着它依赖的更新会一直被拒，这本书的同步停到重启为止，书本身完好。
- **`entry.update`、`module.set_field` 自己在大书上要几百毫秒：已修（2026-11-13，随一种条目的数据层）。** 原因是写入前的 `graph_ok` 每次把全书的自动链接名字两两比一遍（约占 94%），而且整本重验会把读取时容忍的旧冲突当成新错误：另一台设备同步进来一个同名人物之后，这本书里所有写入都被拒。现在写入前只比改前和改后、只拒绝这次写入新造成的违规，名字表一遍扫出。改标题在重型种子上 219 → 7 ms，三年的书上 406 → 12 ms；改一个字段 246 → 2 ms、402 → 2 ms（三年那一列里也有书目文档变小的份）。回归：`a_duplicate_name_a_merge_left_blocks_no_unrelated_write_and_a_rename_resolves_it`、`a_nested_manuscript_a_merge_left_blocks_no_unrelated_write`、`writes_that_change_many_entries_refuse_only_the_duplicates_they_make`。
- **帮手每次工具调用把书目文档整本拷贝 3–4 份，而且拷贝特别贵**（2026-11-13 量的，三年的书）：名字解析 `resolve_v3` 两次共 567 ms，写后工具目录重建 662 ms（每次写都让缓存失效，重建时又反复解码全书），写前快照选条目 `checkpoints::entries` 250 ms（`entry.update` 这类调用根本用不到那份拷贝）。拷贝贵在 `dr-store` 的 `load_into` 把快照和之后的更新一起交给 `import_batch`：只有快照时 18–23 ms，多一条小更新就是 224–235 ms，先导快照再导更新是 85 ms。`load_into` 和 `checkpoints::entries` 这两处已修（2026-11-13）：载入改成先导快照、再逐条导更新，三年的书每份拷贝降到 90–100 ms；写前快照选条目只在要查关系、归属、补丁时才拷贝。三年的书上帮手「读后改标题」从约 2.2 秒降到约 1.3 秒。名字解析和工具目录带着层级语义，等统一条目的数据层落地后再改。
- **历史不裁剪。** 载入、打字、体积都没有量出逼我们裁的东西；浅快照解决不了撤销，还会让历史点、同步、批注锚点失效。

## 监管会话替作者定下的小事

仍然有效的。

- 界面和 Agent 对同一操作语义分叉的地方，统一成一条命令；Agent 的写入直接生效，靠快照历史撤销。
- Agent 对话照旧同步：每个对话一个只追加的 Loro 文档；运行日志、事件、权限只在本机。
- Windows 上「关窗后留在通知区」用 tray-icon crate 保留。
- 字数统计按真实文字数，不复现旧版「加粗切开的拉丁词算两个」的偏差。
- 身份文件里加机器指纹（macOS `IOPlatformUUID`、Windows `MachineGuid`），指纹变了就当新设备，用来抓「迁移助理连身份文件一起拷走」。新电脑在写作日里算新设备。
- `runtime_shaders` 是各可执行文件自己的默认特性，正式包用 `--no-default-features` 关掉；发布前做。
- 正式版身份在交接时加 `release-identity` 特性，只有发布工作流打开。
- 按键上屏的预算拆成两条：「按键到交出画面」照旧 16 / 8.3 ms，发布档靠 GPUI 补丁；「按键到真正显示」只记录。想拿 TextEdit 当参照要往它发模拟按键，会动到作者电脑上的另一个应用，重测时先问作者。
- 性能数字只在机器空闲时量才算数；多路并行编译时量的只作参考。
- 空闲 CPU 约 1% 是 GPUI 的 CVDisplayLink 空转，探针档接受；发布档之前用补丁停掉。
- 组字中失焦：清掉组字，不原样上屏。
- 组字规则是独立的 `gpui-ime`，断行是独立的 `prose-linebreak`，编辑器、输入框、PDF 导出共用。
- 重锚和待办投影不进对象级撤销日志。
- 菜单栏先保持英文。
- 「冷启动到书架」从可执行文件开始运行算起，不含 Launch Services 的那一段。
- 旧 Agent 对话只读搬过来；没经过交接的旧库默认拦住，同时给「仍然导入」。
- 上游问题：复现过、查过重、确认不是用错了接口，就直接开 issue 再报链接；开 PR 和在别人的 issue 里表态仍然先问作者。
