# 统一条目（内核 v4）：八条并行轨道的任务书

2026-11-13 监管会话写。给接手这八条轨道的会话用：每条轨道一个会话、一个 worktree、一条分支。作者把你分到哪一条（T1 到 T8），你就读「公共部分」加自己那一节。

这是过程文档：八条轨道都合进 `main` 以后删掉，仍然有效的规矩并回 [README.md](README.md)。

## 公共部分

### 这轮在改什么

`next/` 的数据模型原来把条目写死分成「层级」和「叶子」两种。作者 2026-11-13 推翻了这个两分：**只有一种条目**，任何条目都可以由模板随意拼模块，「下面能不能放东西」是条目上的一个开关。同一次格式改动里，写作日和快照点清单各挪进每本书自己的一篇小文档，书目文档的格式升到 4。

完整设计在 [kernel-v4.md](../kernel-v4.md)。数据层（`dr-model`、`dr-doc`、`dr-workspace`、`dr-testkit`）由另一个会话先做完；它只对界面、帮手、导入、导出做了「能编译、测试能过」的最小改动，剩下的就是这八条轨道。

### 开工信号：等数据层合进 `main`

**数据层没合进 `main` 之前不要动手。** 信号是本地分支指针 `ready/kernel-v4-data-layer`（监管会话在数据层合进 `main`、合并后的树上全套检查通过时建）：

```bash
git -C ~/Drifting rev-parse -q --verify refs/heads/ready/kernel-v4-data-layer
```

- 命令有输出（一个提交号）、退出码是 0：可以开工。
- 没有输出：还没好。**每 10 分钟查一次**，其间不建分支、不建 worktree、不改任何文件、不构建。
- 等的时候可以只读地预习：`AGENTS.md`、[README.md](README.md)、[progress.md](../progress.md)，以及设计说明的草稿（它在数据层合进来之前还不在 `main` 上）：

  ```bash
  git -C ~/Drifting show chihumyum/next-unified-entry-7d55f5:docs/rust-rewrite/kernel-v4.md
  ```

- 不要凭猜测开工：`main` 上出现了 `kernel-v4.md`、或者某个提交说明里写了 v4，都不算信号，只认上面那个指针。
- 等了 12 小时还没有信号，就停下来报告，不要自己去做数据层。

信号出现以后：

```bash

git worktree add ~/Drifting-v4-<轨道> -b codex/v4-<轨道> main
```

`<轨道>` 见各节（比如 `t1-shell`）。然后先读 `main` 上的 `docs/rust-rewrite/kernel-v4.md` 全文，尤其是它末尾「数据层交回：留给各轨道的缺口」里属于你的那一段。**本页和 `kernel-v4.md` 说法不一致时以 `kernel-v4.md` 为准**，并在交回报告里指出来。

### 作者已经定下的（不要再议）

1. 只有一种条目。模块任意拼（正文可以多篇、字段、键值表、补丁、情节规划、关联、「下面的条目」）。
2. 开关在界面上叫「**层级**」，旁边一行小字「打开后下面能放条目」。开关是条目自己的属性，模板只给新建时的默认值。
3. 开关打开后才显示只对「下面」有意义的设置。「允许放哪些模板」这项设置没有了；要选的只有「在这一层新建时默认建什么」。
4. 下面还有条目时关开关：界面提示，作者继续就把下面的条目移到最外层（一条原子命令，一步可以撤销）。归属、泳道身份、设置都不删，再打开就回来。
5. 一个条目可以有一篇或多篇正文，**每篇各自有一个开关**，决定这一篇是否计入字数、是否参与导出。
6. 导出和整书视图里，条目自己的正文排在它下面的条目之前。导出时，自己没有成书正文的中间层（比如「第一卷」）的标题这一轮不出现。
7. 整书视图重做：从任何一个开着开关的条目出发，摊平看它和它下面的全部内容。**挂名（归属）进来的也算**，按归属自己的顺序排在住在下面的条目之后。成书、导出、全书字数仍然只看住处。按章写死的旧「纵览全书」退役。
8. 「下面的条目」是一个模块。显示方式**维持现有四种**（列表、网格、看板、岛屿），这一轮不加新样式。
9. 新书的模板列表里多一个「幕」模板。
10. 模板更新与项目无关：项目建好以后，内置模板怎么变都不影响它，不做升级通道。
11. H1/H2/H3 是正文内部的结构，不是条目层面的结构。只叫 H1/H2/H3，不要为「把标题当条目」设计任何东西。
12. Markdown 文件夹（`dr-mirror`、M40）这一轮不动，以后按新结构重新设计。
13. 格式干净改：不并读、不写迁移、不留兼容垫片。新模型让哪些代码和测试失去意义，就删掉。
14. 先把结构弄对、功能可用。长相以后再打磨：不要自己设计新的视觉样式，沿用现有组件；不要加作者没要的说明文字、提示句、选项描述。

碰到必须作者定的新问题：写进交回报告的「等作者的事」，按你认为最保守的做法先做，**不要停工等**。作者白天集中答这些问题。

### 规矩

先读仓库根的 `AGENTS.md` 和 [README.md](README.md)（「做的时候」「真窗口验收」「不能替作者做的」三节全部适用）。这里只强调最容易出错的：

- **不推送、不开 PR、不合 `main`、不打标签。** 提交说明用英文，不加署名行，按步骤分开提交。
- **不碰 0.1 客户端**（`src/`、`src-tauri/`、`crates/`、`drizzle/`）。不读作者的日常书库和真实稿件；不连真实服务；不调真实模型接口；不装任何系统组件。测试数据只用 `dr_testkit::seed`、`dr_testkit::samples`、`dr_testkit::media`。

- **测试**：模型变了，断言旧两分规则的测试换成断言新规则的测试；每删一条、每改一条期望，都在报告里写改前改后和原因。不许为了通过而放松断言、加重试或 `#[ignore]`。
- **跟上 `main`**：交回前 `git merge main`，在合并后的树上跑检查。
- **日志和验收证据**放 `~/Drifting-autopilot-logs/v4-<轨道>/`，不放进任何工作区。

## T1 外壳与条目页（`t1-shell`）

- **范围**：`dr-shell`（左栏的树、页面组装、大纲、条目颜色）、`dr-view-page`（开关和确认、「下面的条目」模块、页眉）、`dr-view-elements`、`dr-view-element-overview`。

  - 「下面的条目」模块：按这个层级的显示设置画住在下面的条目和归属进来的条目。模板里没有这个模块而开关开着时，排在页面最后。显示方式只有现有四种。
  - 「下面」的设置面板：只在开关开着时出现。（「允许的模板」一行和它的文案键，数据层已经删了。）

  - 数据层留在这几个 crate 里的缺口（按 `kind`、`allow`、`about` 写的分支）全部收掉。
- **回归测试**：开开关、关开关（有无子条目）、确认后子条目到位、撤销一步回去；模板没有「下面的条目」模块时排在最后；设置面板没有「允许的模板」；原来各层级的「说明」作为普通正文照常显示和编辑。
