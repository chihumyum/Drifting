# Development seed workloads and performance/stability validation

Use **lite for quick functional verification**: creation, editing, navigation,
relations, TODO/comment state changes, material notes, attachment previews and
Agent history/recovery. Use **stress when implementing or validating performance
and stability changes**. A lite pass cannot close that heavier validation.

Both presets are written from `src/renderer/services/sample-project/`. They are
separate from the app's [built-in sample project](sample-project.md), the English
*Pride and Prejudice* workspace that every new library (including a fresh
`pnpm dev` or `pnpm dev:worktree` profile) gets on first launch. That sample is
a real novel of about 122,000 words with a curated workspace and no Agent
history; it is not a performance workload. Use `pnpm dev:seed:lite` for the
synthetic corpus with Agent discussions.

The stress preset has 3.5 million words across chapter, element, inspiration
and material-note bodies, plus storyline/category prose, review work and large
Agent histories. Its longest chapter is 20,000 words, element 10,000,
inspiration 50,000 and note 10,000. The longest Agent discussion has 600 rounds,
including tool cards and long results. The full [preset table](worktree-development.md#seeded-profiles)
and [generated corpus evidence](dev-cli/acceptance/seed-presets.json) define the
current workload; the old short-prose seed is not a substitute.

## Development workflow

1. Run the appropriate unit/integration checks and smoke-test the implementation
   in a fresh profile (`pnpm dev:worktree --instance <new> --no-watch`, which
   opens with the built-in sample) or with `pnpm dev:seed:lite --no-watch` when
   the synthetic corpus or Agent history matters. Confirm the intended behavior before attributing a
   failure to data volume.
2. For a performance/stability implementation, run the same affected journey
   with `pnpm dev:seed --no-watch`. The seed wrapper delegates launch to the
   isolated worktree launcher. For automated desktop acceptance after seeding,
   use `pnpm dev:worktree --instance seed-stress-v2 --no-watch`. Rebuild and launch
   the current Debug app for this checkout; record its exact source/binary
   identity. The old app bundle has no acceptance value for new code.
3. Capture a baseline before the change and a candidate afterward with the same
   corpus recipe, build mode and machine. Use separate instances such as
   `perf-before` and `perf-after` when both are needed. Keep each instance's
   database, assets, port and application identity independent. Avoid measuring
   while another build, seed import or profiling run competes for resources.
4. Record the actual operation boundaries and run sequence. Separate initial
   compilation/seeding from app startup, cold project opening, first document
   hydration and warm navigation. Collect raw samples before summarizing p50,
   p95, worst case and sample count. Repeat the affected warm journey at least
   five times; a single favorable sample is insufficient.
5. Run repeated navigation/edit/close/reopen cycles with stress data. Verify
   that contents, word counts, relation endpoints, TODO/comment states and
   canonical Agent history survive. Record failures, stalls, memory trend and
   recovery outcomes alongside timings. Keep the evidence generated by its
   collector; do not edit a measurement JSON to make it pass.

## Journeys to cover for the changed subsystem

| Subsystem | Stress journey and observations |
| --- | --- |
| Startup/workspace | Shelf to project; cold and warm open; capture/projection time, SQL/IPC counts and payload sizes, time until the affected surface is usable |
| Writing/Yjs | Shortest and longest chapters, the 50k-word inspiration, 10k-word element/note; initial hydration, selection, typing/IME, undo/redo and durable save |
| Tabs/whole book | Open several long documents, alternate/split tabs, whole-book scrolling and chapter jumps; frame delays, retained editors/subscriptions and memory after closing |
| Lists/graphs/search | All categories/elements/inspirations, storyline memberships, relations and TODOs; filters, search, drag/selection and list/graph updates |
| Materials | Long checklist notes, folder changes, repeated attachment preview/open/close; resource disposal and persisted state. Use a separate synthetic large-file corpus for PDF/image decoder limits |
| Agent | Switch among short and 600-round discussions; restore, scroll and expand long tool results; canonical replay cost, transcript rendering, memory and listener cleanup |
| Restart/recovery | Finish a save, stop the owned app, relaunch the same profile and reopen the affected objects; verify persisted prose/history and state. Exercise interrupted-write recovery only through the documented failure-injection harness |

A feature need only cover the affected journeys, but its acceptance notes must
state which stress surfaces were exercised and which remain unmeasured. Do not
present seed generation time, a passing unit suite or a corpus-size audit as
application responsiveness or stability measurements.

## Observation and diagnosis

Debug desktop builds automatically run the [stall watchdog](renderer-performance/dev-stall-watchdog.md).
It uses a 250 ms heartbeat and writes `logs/renderer-stalls.log` beside the
profile's database directory. It reports long renderer stalls even when the
WebView never recovers, with recent input, editor size, IME state and labelled
work. On macOS, `logs/stall-samples/` holds native WebView stack samples.
Absence of one-second stalls does not establish smooth typing or scrolling.
The optional [native heavy-seed audit collector](renderer-performance/stress-seed-native-audit.md)
adds bounded React, input/frame, DOM and IPC observations plus owned-process
RSS/CPU sampling. Its coverage report must distinguish completed native
journeys from unavailable or unmeasured surfaces.
The [2026-10-29 diagnostic record](renderer-performance/stress-seed-audit-findings-2026-10-29.md)
also provides a repeatable CPU/retention/persistence probe against the actual
heavy library. Its Node results are separate from native UI acceptance.
The [native continuation](renderer-performance/stress-seed-native-findings-2026-10-29.md)
records the 25-tab run, real writes/relations/media, a watchdog-confirmed stall,
post-restart canonical checks and the remaining coverage gaps. Use those concrete
journeys when validating a performance implementation; keep its Debug numbers
separate from any subsequent release baseline.

When implementing a potentially expensive operation, add bounded development
activity labels (`beginDevActivity`) and, where needed, a focused timing/counter
collector around that operation. Record duration, counts, sizes and correlation
ids without manuscript text, credentials or personal paths. Preserve a read-only
measurement path and existing transaction/flush boundaries. A label overlapping
a stall is a lead to investigate, not proof that it caused the stall.

For sub-second interaction problems, measure the relevant dispatch/commit,
long-task/frame delay and actual visible-result boundary. Account for SQLite,
IPC, Yjs decode/apply, derived scans, React work and layout separately when the
hypothesis crosses them. State whether the endpoint is a requestAnimationFrame
callback or a compositor-visible result. Sentry currently covers errors and
selected diagnostic operations; it is not a replacement for this local trace.

The independent `perf:renderer`, `perf:renderer:lifecycle` and Rust/database
benchmarks remain useful focused tools. They use their own synthetic fixtures;
they do not automatically exercise the stress seed. Check their source hooks
before collecting new evidence: the historical native startup collector has a
stale bootstrap source anchor. Keep Chromium/headless, native WKWebView,
simulator and physical-device conclusions separate. Establish thresholds from
the relevant baseline and an explicit feature budget; this workload does not
invent a universal latency or memory pass threshold.

## Corpus integrity acceptance

```bash
pnpm seed:acceptance
pnpm seed:acceptance --check
```

The first command creates real migrated synthetic libraries for both presets,
reconstructs every book/element/inspiration/storyline/category Yjs body, measures
fresh material JSON, and validates exact totals, length endpoints, cached node
counts, foreign keys, asset ownership/verified receipts and Agent recovery.
It retains disposable fixtures under ignored `.local-data/seed-preset-acceptance`
and generates `docs/dev-cli/acceptance/seed-presets.json` without personal paths
or manuscript content. The second checks that evidence against the current
seed source fingerprint and preset contracts. Neither command opens a desktop
window or measures UI latency, FPS, peak memory or endurance stability.

Every first-run seed performs the same audit before publishing its staging
library. Existing profile libraries are preserved, including user edits; choose
a new instance for a clean recipe. Preset versions select different default
instance names, so a new stress workload does not silently reuse old tiny data.


## 重型数据下的实现回归

[2026-10-29 修复记录](renderer-performance/stress-seed-performance-fixes-2026-10-29.md)列出基于原生走查落地的实现：后台投影 Worker 化并保持捕获/原子发布边界、素材有界摘要与视口加载、搜索结果窗口化、隐藏标签与侧栏订阅收窄、离线长对话历史分段显示，以及章节/构想计数修正。

重型 Seed 用于这些性能与稳定性路径的复测；轻量 Seed 仍用于快速验证功能，不能用轻量数据的顺畅程度替代重型验收。新增代码后先通过正常检查，再单独采集原生性能，避免基准与测试/构建争抢 CPU。保存后的 Yjs、Markdown manifest 文件哈希、关系及 SQLite 完整性由只读脚本复核；浏览器 Agent 回归覆盖 100 次面板开关、流式选区/滚动、异步历史和离线发送限制。

进一步的交互预算、10 倍负载矩阵、文档/视图生命周期与本地数据架构演进见[重型工作流方案](renderer-performance/heavy-workflow-architecture.md)。本轮快照复用与隐藏视图渲染隔离的证据分层记录，未将合成测试等同于原生流畅度达标。
