# 重型 Seed 交互基线（`pnpm perf:stress`）

## 用法

```bash
pnpm perf:stress --foreground            # Debug：Rust debug + Vite 开发版渲染层（React Strict Mode）
pnpm perf:stress --release --foreground  # release：Rust release + 生产版渲染层（dev:worktree --release-perf）
pnpm perf:stress --compare a.json b.json # 对比两份报告的核心指标
```

### 运行流程

1. 启动 `perf-stress` 隔离实例。首次运行会生成重型 seed，之后每次运行前都把数据库恢复到 seed 刚生成时的快照。
2. 通过前端调试桥依次执行 `scripts/perf-stress-journeys.js` 中的操作：
   - 打开项目、打开两万字章节、空闲；
   - 末尾打字、中段打字、滚动；
   - 展开侧栏后再打字、切换侧栏面板；
   - 打开 12 个标签，并在侧栏开、关两种状态下各切换 12 次；
   - 全局搜索、通览全书、三个 Super View、关闭全部标签。
3. 每段操作前后，记录原生进程和 WebContent 进程的 CPU 时间与 RSS。
4. 最后点应用菜单的「退出」，确保退出前的保存流程也被计入。

报告写到 `.local-data/perf-stress/<label>.json`，不含路径和正文。

### 注意事项

- **加 `--foreground`**：每段操作前把窗口拉到最前，一次约 3–4 分钟，期间不要操作电脑。
- **不加 `--foreground`**：只有 CPU、内存和完成时间可信。窗口不在前台时，WebKit 会把帧节流到每秒约 3 帧，被遮挡时完全停帧；报告会标出没有焦点的段落。
- **操作方式**：所有操作都通过 DOM 模拟完成，没有走真实键盘和输入法。
- **WebContent 进程**：WebKit 不标明某个 WebContent 进程属于哪个应用，所以脚本把和应用同时启动的那个 WebContent 进程当作本应用的。报告里的 `webContentCandidates` 记录候选数量，为 1 时结果可靠。

## 结论

### release 构建基本解决的

- **后台 CPU**：Debug 下编辑器空闲时，原生 CPU 偶尔到 46%（刚打开项目时的后台工作）；release 稳定在 3–5%。
- **原生端每次按键的开销**：打字时原生 CPU 从 Debug 的约 68% 降到 31%。之前在 Debug 下看到的保存路径开销，大半来自 Rust 未优化编译。
- **原本就够快的**：全局搜索、全书滚动、章节滚动、打字延迟，在两种构建下都已经流畅，不需要优先处理。

### release 构建下依然存在的

- **切换、打开、关闭标签，展开侧栏，打开 Super View 时的单帧冻结**，大约 60–300 ms：
  - 切换标签单帧约 50–60 ms，开着侧栏时 p95 约 120 ms；
  - 展开侧栏约 160–180 ms；
  - Super View 130–210 ms；
  - 关掉最后一个标签约 310 ms。

  这些在 release 下几乎没有改善，主要是 WebKit 的样式和布局工作，与 React 构建模式无关。
- **打字时 WebContent 的 CPU 占用**：release 下约 73%，按每秒约 8 个字算，每个字约 140 ms CPU，还高于 Debug。打字延迟不受影响（p95 约 30 ms），但会耗电、发热。目前还不知道这些 CPU 花在哪里。
- **内存**：开 12 个标签，再打开全书和三个 Super View 后，WebContent 内存到约 1.5 GB。

### 后续优化顺序

1. **标签和侧栏的冻结，同时控制内存**：给常驻编辑器设上限，超过的释放成轻量快照；去掉切换路径上同步读尺寸、强制排版的代码；收窄侧栏面板的重新渲染，要素等长列表只渲染可见部分。
2. **打字时 WebContent 的 CPU**：先用 Web Inspector 时间线或原生栈采样，分清是 JS（Yjs 编码、字数和大纲统计）、长文档重新排版还是 GC，再动手改。
3. **Super View 首次打开**：预取延迟加载的代码块，长列表只渲染可见部分。
4. **关掉最后一个标签回到项目主页、打开项目**：各约 300 ms。
5. **投影的原生发布**：只在停笔后运行，暂不优先。

每一项都用 `pnpm perf:stress --release --foreground` 测出改前改后两份报告，再用 `--compare` 对比。
