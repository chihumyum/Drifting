# Markdown 投影：停笔后再跑，只读改过的正文（2026-10-29）

## 问题

自动投影原来在第一次提交后 1 秒触发，并且不会因为继续打字而推迟。持续打字时，大约每 3 秒就把整个项目导出一遍。每次导出都要做这些事：

- 刷新所有打开的文档。
- 读出全项目的 Yjs 正文；重型 seed 约 12 MB。
- 读出全部 `node_content` JSON，约 4.6 MB。
- 在 Worker 中重新水合并渲染全部文档。
- 由原生端发布。

[资产绑定校验修复](asset-bind-validation-reads.md)的复测发现，打字时原生 CPU 主要消耗在这里。

## 修复

- **调度**：自动投影改为在 2 秒内没有新提交后才运行；如果作者一直不停，距最早一次未投影的改动满 30 秒时也会运行。输入法组字时延后，每 1 秒检查一次。手动刷新和生命周期刷新不受影响。
- **后续调整（同日）**：停笔窗口改为 5 秒。关闭项目时，以及退出 App 前的生命周期刷新中，若有尚未投影的改动或上次失败，会立即补一次捕获；没有待投影内容时退出不再重复导出。重新打开同一项目时，会先等关闭时那次捕获发布完。
- **增量捕获**：
  - 渲染 Worker 改为随项目常驻，按 Yjs `revision:updatedAt` 缓存每篇文档水合后的 prose JSON。
  - 捕获时先读一次 `yjs_document_revision`，只为版本变化的活跃文档读取 Yjs 字节和 `contentJson` 种子。
  - 缓存与捕获对不上时，本次投影失败并清空缓存，下一次完整捕获；不会用旧正文或种子顶替。
  - 关闭项目时终止 Worker，释放缓存。
  - 导出 ZIP 等不传版本的调用仍然完整捕获。
- **原生发布不变**：仍会重新校验全部附件，并逐个比较输出文件。

### 测试

- `markdown-projection.service.test.ts`：等待停顿、30 秒上限、运行中不重叠。
- `markdown-projection-client.test.ts`：Worker 跨捕获常驻；失败或中止后丢弃缓存。
- `relational-markdown.acceptance.test.ts`：增量渲染与完整渲染逐字节一致；缺失缓存时拒绝渲染。
- `relational-markdown.local-source.integration.test.ts`：用真实 SQLite 验证只读取版本变化的文档、跳过回收站文档、保留无 Yjs 文档的种子。

## 实测

### 测试条件

- 实例：同一重型 seed 实例，第 007 章，约 2.2 万字。
- 构建：Debug + Vite + React Strict Mode。
- 窗口：可见但不在前台，不节流定时器。
- 方法：同一会话内替换新旧实现并重载页面，各跑两次。
- 流程：先输入一个预热字符并等待 12 秒，然后连续输入 30 个字（约每 0.38 秒一个），再静置约 12 秒。

### 打字窗口（约 12 秒）

| | 旧实现 | 新实现 |
| --- | ---: | ---: |
| 投影运行次数 | 2 / 3 | 0 / 0 |
| 原生 CPU 占用 | 67% / 89% | 21% / 19% |
| WebContent CPU 占用 | 34% / 44% | 30% / 26% |
| WebContent RSS | 1.05 / 1.17 GB | 0.60 / 0.57 GB |

### 停笔后的一次投影

| | 旧实现 | 新实现 |
| --- | ---: | ---: |
| 耗时 | 2.1 / 2.3 s | 1.26 / 1.37 s |
| 其中原生发布 | 0.75 / 0.8 s | 0.91 / 0.99 s |

### 捕获本身

在页面中直接调用三次：

- 完整捕获：1.08–1.13 s。
- 增量捕获（无改动）：0.21–0.22 s。剩下的时间用于读取结构化行。

### 真实数据核对

同一数据库状态下比较 manifest，755 个文件中只有 `开始阅读.md` 不同，原因是其中写有生成时间；文档映射也一致：

- 新实现：编辑一次后做增量投影。
- 旧实现：完整导出。

## 剩余开销

- **停笔后的投影**：现在主要花在原生发布上，每次约 1 秒。它会重新读取并校验全部附件，逐个读取并比较输出文件，再计算 manifest 哈希。
- **打字本身**：原生 CPU 约 20%、WebContent 约 26–30%，这部分没有投影参与。
