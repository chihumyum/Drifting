# Copilot 工作方式改造计划

日期：2026-09-05

状态：**实施计划已记录；下述改造尚未实现。** 当前已有 Copilot 继续存在；本文件不代表新调度、新交互或新验收已经交付。

本计划将 Copilot 调整为围绕作者当前写作片段工作的轻量助手。工作顺序为：收集相关变化、判断本次是否值得帮助、校验证据与版本、选择呈现时机、记录作者决定。

阶段、依赖和验收要求见人工维护的 [计划清单](acceptance/redesign-plan.json)。该 JSON 是计划源文件，`evidence` 初始为空；它不是生成的能力清单，也不是通过验收的证明。实施时，每个阶段必须同时提交实现、行为测试、文档更新和可复现证据，才可改为完成。

## 1. 产品职责

| 层次 | 负责的问题 | 交互和权限 |
| --- | --- | --- |
| Copilot | 当前句子、段落、场景，以及作者正在处理的局部问题 | 就地提问、准备修改、少量及时建议；正文和 Canon 变更由作者明确接受 |
| Ambient Editor | 作者指定关注点下的持续阅读、跨章节影响和待复查事项 | 后台只读分析，维护有证据的 Concern；使用共享 Agent Runtime |
| General Agent | 作者明确委托、需要持续执行的任务 | 持久对话、检索、工具执行和既有审阅权限 |

Ambient 仍为 [未实现的目标设计](../ambient-editor/README.md)。本次 Copilot 改造不依赖完整 World Model，不实现 Ambient Concern 或 Review Debt，也不恢复 Shadow CI、Element Arc、Goal Evolve。全书观察仍归 Ambient；长任务执行仍归 General Agent。

共享范围优先是原文读取、源版本、证据锚点、相关上下文和作者决定的查询接口。现有 Copilot 单次请求先复用其 renderer-local BYOK 路径；需要 Agent 工具时组合现有 renderer-owned Runtime 的受限能力，禁止再造 provider 执行循环。Copilot Provider 与 General Agent composer 的 Provider 分别保持作者选择，无隐式切换。

## 2. 作者最终会看到的变化

| 当前行为 | 目标行为 |
| --- | --- |
| 停顿固定秒数后分别运行提取、演变检测 | 合并本轮相关编辑，判断是否产生值得分析的新信息；时间只控制稳定窗口和调用频率 |
| 摘要覆盖决定检测原文范围 | 每项能力独立记录处理版本；摘要只压缩上下文 |
| 两项能力各自反复发请求 | 在同一有效快照上完成一次受限的机会判断和候选生成，允许返回“无建议” |
| 模型结果返回后直接生成批注 | 先校验证据、源版本、重复事项和作者决定，再按作者注意力选择展示 |
| 用户调整毫秒级延迟 | 用户选择“仅手动”或“适度辅助”，决定是否需要新元素和演变建议；精确节流参数由系统管理 |
| 自然语言输入默认执行修改，讨论要另选菜单 | 保留明确动作入口，同时让通用输入理解“回答／准备修改”；始终显示动作和范围 |
| 讨论随弹窗关闭消失 | 同一写作会话中可回到讨论；需要持续任务时携带上下文转交 General Agent |
| 拒绝按名字或临时标题处理 | 区分“本次不要”和明确的长期偏好；同一事项的后续建议尊重已有决定 |

示例：作者写到一个新名字，不必立刻建议登记。后续行动、关系和身份使它成为值得管理的人物时，模型可以给出带原文证据的登记建议。作者继续打字时先延后展示；作者拒绝本次提议后，同一依据不再重复。新的实质信息出现后可重新评估，明确的长期禁用偏好仍然生效。

停顿、反复修改、选中文字只能作为操作信号。系统不得把它们直接解释为“作者卡住了”“这段写得不好”，也不得因此自动续写或改文。

## 3. 新工作流程

### 3.1 收集本轮编辑

- 只由当前可交互编辑面持有观察权，避免相邻预览、虚拟列表、重复挂载触发同一工作。
- 记录当前章节、被修改的块及变更前后内容、选择范围、相关元素／演变变化；以 Live Yjs 和真实编辑事务为来源。
- 区分本地输入、输入法组合、撤销重做、同步应用、Agent 修改、文档初次加载和纯格式变化。所有来源都参与失效判断；自动分析优先跟随本地作者编辑，远端／Agent 变化不自行制造一轮新弹出。
- 同一区域的连续编辑合并为一轮。离开段落、短暂稳定和手动请求可推动调度；进入新章节不会自动扫完整旧稿。
- 一轮分析有明确的源依据，包括正文内容与结构、相关领域数据、作者决定和策略版本。文字未变但相关决定变化，也能正确失效。

### 3.2 判断是否可以运行

- 无新增有效依据、输入法尚未提交、已经处理相同版本、手动请求正在进行、Provider 不可用或预算不足时，不发自动请求。
- 每个活动项目至多一个自动分析请求；新编辑合并到下一轮，手动调用获得优先权。过期结果一定丢弃，取消请求只是节省资源的辅助措施。
- 定时器是可注入、可测试的节流参数；它不决定文学价值。自动请求有冷却、次数和 token 上界，具体默认值须由 P5 的实际测量确定并记录，不能以调小延迟冒充更智能。
- 自动关闭时，不维护待发送的模型请求；手动功能独立可用。设置面板里的“暂停本次写作”保留作者长期偏好。

### 3.3 判断是否值得建议

- 在一个受限结构化调用中，同时完成机会判断和候选内容生成，不增加每次必经的额外“是否调用模型”模型。
- 输入包括当前片段、实际变更、必要邻文、相关元素与已接受演变、待处理事项及拒绝依据。小章节可直接使用全文；大章节按任务相关性和 token 预算构造上下文，摘要必须有有效版本。
- 输出只能是 `no_op` 或允许的建议种类；必须携带证据、目标和本次新增信息。不要让模型自由指定工具权限、扩大项目范围或编造事实。
- 首轮仅支持现有 `element-candidate` 与 `element-patch`。局部文风、节奏、情节判断仍通过手动提问；自动文学批评不是本轮上线条件。
- 模型自报置信度只作为内部参考，不作为已校准概率展示，也不能单独决定是否呈现。
- 无建议是正常完成，可记录本次有效依据以避免重复调用；错误、取消、失效和持久化失败不能伪装成已处理。

### 3.4 校验与呈现

- 请求返回、准备落库、准备呈现和作者接受时分别核对所需源依据。证据不存在、目标删除或依据变化时失效，并以当前内容重新准备。
- 先在内存中形成经过校验的候选，合并重复事项。真正进入待审阅状态才持久化到现有 Comment／Review 路径；不把每次模型输出都变成一条批注。
- 作者持续输入、正在讨论或审阅时延后主动提示。弹窗关闭后重新检查待呈现内容，不能因一次跳过就永久丢失，也不能直接展示期间已过期的结果。
- 同一时刻至多主动提示一项。复用现有批注和编辑器反馈位置，不增设第二个 Copilot Inbox，不自动打开 Rail、滚动页面、抢焦点或每次发送全局完成通知。
- 持久化但未主动提示的建议仍可在已有 Review 入口找到；正文变化后更新／标记其有效性。延迟呈现不等于丢失作者可查看的事项。

### 3.5 学习作者明确表达的决定

- “本次不要”只抑制同一事项、同一有效依据；有实质新证据时可以重评。
- “不要再建议登记这个名字”等长期偏好必须由作者明确选择，具有项目范围，并可查看和撤销。
- 不将忽略、关闭弹窗或一次拒绝推断为永久写作规则。
- 已接受演变及已有待处理提议纳入后续判断；同一事项尽量更新已有提议，不能依赖模型标题相同才去重。
- 稳定身份使用确定性领域字段和证据锚点；对于语义等价但表述不同的演变，先做候选匹配再验证，不能直接把模型自由生成的 ID 当唯一键。

## 4. 数据与一致性边界

| 数据 | 所有者与生命周期 |
| --- | --- |
| 正文、正文修改 | Live Yjs；自动化写入通过现有正文写入／live document 路径 |
| 当前编辑轮次、定时器、临时候选、已处理版本缓存 | 本地会话状态，可丢弃重建，不同步，不冒充 Ambient Review Debt |
| 摘要与摘要有效性 | 可重建的派生数据；不能决定另一能力是否已经工作 |
| 已呈现／待审阅建议、接受／拒绝决定 | 既有 SQLite Comment／CommentAction 与 SyncEngine 路径；需要扩展时使用明确版本化结构 |
| 项目内长期辅助偏好 | 作者数据；P3 明确其持久化／同步归属，不能只藏在组件状态或模型提示里 |
| 手动临时讨论 | P2 保留在本次应用会话的项目／锚点范围内，可主动清除；不承诺重启恢复 |
| 转交 General Agent 的任务 | 作者确认发送后进入其既有持久对话与权限体系 |

正文修改必须核对生成时的原文和目标结构。局部选择使用可验证的锚点，不能只依赖旧绝对坐标；多块修改要求目标全部存在且仍匹配，禁止悄悄只应用剩余部分。校验和写入之间不得留下可插入异步变更的窗口。字符格式、链接、块 ID、层级和撤销行为属于验收范围。

建议接受的领域变更与终态记录需要幂等操作身份和可恢复边界，避免领域写入成功、记录失败后再次接受造成重复元素／演变。具体实现优先复用现有用例和原子事务能力。

任何新增持久状态必须先检查实际 schema、迁移序号和同步域。不得修改已发布的 `drizzle/0000_local_first_baseline.sql`，不得占用其他工作已经新增的迁移号；需要 migration 时追加下一可用序号，经过 native SQLite 安全快照和失败回滚验收。派生的运行缓存与作者决定分别处理，不能为了缓存重建而清除作者反馈。

## 5. 分阶段实施

### P1 — 修复可靠性

目标：已有能力先正确处理原文，不遗漏、不使用过期结果覆盖作者内容。

改动：

- 拆开“摘要覆盖”和“能力处理版本”，两项检测分别跟踪所需依据。
- 部分失效摘要不再把已经失效的叙述混入当前事实；优先回到有效原文或重建摘要。
- 加入请求、候选、落库和应用时的版本／锚点校验；修复旧请求返回及多块修改部分成功问题。
- 收紧接受的幂等和事务边界；鉴权错误、取消与失败有正确终态，手动请求不会无声挂起。

主要落点：`hooks/useCopilot.ts`、`lib/copilot/coverage-map.ts`、`base-block-context.ts`、`produce-block-section-summary.ts`、`inline-edit.ts`、`usecase/useComment.ts` 和共享 Review 接受路径。

验收：

- `C01`：在提取、演变、摘要任意完成顺序下，每项启用能力都处理其应处理的原文，摘要不能使另一项跳过。
- `C02`：输入、撤销、同步或 Agent 修改使旧结果失效；部分陈旧摘要不能作为当前事实进入请求。
- `C03`：过期坐标／原文、目标删除、部分块缺失时拒绝旧修改；有效修改保留既有格式与结构，并可一次撤销。
- `C04`：接受中断／重试不产生重复领域变更；失败不标记已处理，手动任务均有可见终态。

交付范围：可独立交付可靠性修复；尚不宣称智能调度或新自动建议体验上线。

### P2 — 改善手动辅助和转交

依赖：P1。

改动：

- 保留快捷键、选区／光标入口和显式动作；通用输入支持自然语言判断“提问／准备修改”。意图不明确时先回答或在原入口澄清，不直接写正文。
- 展示当前操作范围；移除把“帮我想”等宽泛词直接判成续写的客户端拒绝规则，保留作者对生成新情节的明确选择。
- 提问可继续讨论；“按这个建议改一下”携带当前讨论形成修改预览，用户接受后应用。
- 关闭再打开可回到本次会话的讨论，重新检查原文有效性；切项目、切锚点不混用历史，清除和退出应用的边界清晰。
- “交给 General Agent”先准备可审阅任务，包含原文锚点／版本、必要原文、问题、相关讨论和作者要求。显示 General Agent 当前 Provider，作者确认发送后才开始执行，不转移 Copilot 的权限。

主要落点：`components/copilot/CopilotInlinePopover.tsx`、`store/copilot-inline-store.ts`、`lib/copilot/inline-ask.ts`、`inline-edit.ts`、`hooks/useEntityEditor.ts` 与现有 Agent composer／conversation 用例。

验收：

- `C05`：“这句什么意思”进入回答；“帮我想想怎么删掉赘词”不被当成续写拒绝；明确修改只生成预览。
- `C06`：选区、当前段、上下文读取范围和最终修改范围一致；自动关闭不影响手动请求，无可用 Provider 时给出明确操作入口。
- `C07`：关闭再开保留同一会话讨论；不同项目不串内容，过期原文明确提示并重新准备修改。
- `C08`：转交草稿可检查／取消，重复点击不重复建任务；实际发送沿用 General Agent Provider、权限和持久化，未发送不调用执行工具。

交付范围：手动体验可独立上线，不等待 Ambient 或新的自动分析。

### P3 — 建立编辑调度和建议生命周期

依赖：P1、P2。

改动：

- 将编辑观察与调度从大 Hook 中分离；引入可测试的编辑轮次、源依据、每能力处理记录及取消／合并状态。
- 区分运行许可、分析结果和呈现许可；实现手动优先、单后台请求、预算限制、切章／休眠／恢复处理。
- 加入稳定建议身份、同依据拒绝抑制、明确长期偏好和已接受演变检索；定义持久化／同步 schema 与迁移需求。
- 将状态限定为可解释的 `pending`、`running`、`deferred`、`ready`、`stale`、`accepted`、`dismissed` 等；开发诊断记录原因，产品界面不展示调度细节。

建议模块职责：`edit-observer` 收集变化，`scheduler` 决定运行，`context-assembler` 准备依据，`suggestion-reconciler` 校验／去重／持久化，`presentation-policy` 决定何时提示。文件名是实施建议，必须结合当前架构边界落位，不建立第二个通用 Agent Runtime。

验收：

- `C09`：IME、纯格式事务、重复挂载和初始化不导致错误自动请求；持续修改可合并，同一依据不重复运行。
- `C10`：手动优先、后台并发上限、预算耗尽、弹窗关闭后恢复和休眠／切项目取消均有确定性时钟测试，无自动重试风暴。
- `C11`：已接受／本次拒绝／长期偏好分别生效；有实质新依据时按范围重评，换标题不能轻易绕过去重。
- `C12`：作者决定重启后保留；如新增同步数据，经过现行领域同步、幂等和有序安全迁移验收；删除可重建缓存不删除作者决定。

交付范围：新调度先通过注入结果的集成测试；不能仅因基础模块存在就默认向作者开放新自动路径。

### P4 — 上线结合上下文的自动建议

依赖：P3。

改动：

- 实现一次结构化调用内的机会判断与候选生成，首轮涵盖新元素和演变建议，允许没有建议。
- 加入相关元素、已有演变和作者决定的有界检索；对原文证据、领域目标和输出 schema 做确定性检查。
- 候选经 P3 的校验／合并后进入共享 Review；持续写作时延迟提示，同一时刻最多主动提示一项。
- 设置调整为“仅手动／适度辅助”、两类自动建议开关、项目长期偏好和“暂停本次写作”。保留既有关闭和分类选择，不自动扩大已禁用的范围；现有 Drift 自动开关继续受尊重。
- 移除用户侧每能力秒数滑块。旧自动关闭映射为仅手动，旧自动开启映射为适度辅助；旧计时值不再当成业务触发规则，迁移不得开启原先关闭的能力。
- 路径切换后移除旧双 debounce 调度，确保没有两个入口同时消费编辑；故障可退回仅手动而保留建议和决定。

验收：

- `C13`：一次新增有效依据至多一个自动机会分析请求；低价值／无新信息允许 `no_op`，模型不能擅自增加写权限或扩大项目范围。
- `C14`：不存在的证据、过期引用、重复演变和被抑制事项不会呈现；自动请求输入和输出遵守记录的 token／数量预算。
- `C15`：输入、审阅和讨论时不抢焦点／滚动／自动开 Rail；延迟结果展示前再验版本，主动提示至多一项，无第二套 Inbox。
- `C16`：旧设置迁移保留关闭与分类偏好；新自动路径独占编辑调度，Provider 不可用时不隐式切换，回退仅手动不丢作者决定。

交付范围：P4 是功能闭环完成，默认扩大使用仍需 P5 的真实体验证据。

### P5 — 真实写作验收与发布

依赖：P4。

改动与验证：

- 将本轮审计复现转换为仓库内的合成回归轨迹，覆盖持续写作、局部修订、粘贴长文、删除段落、拒绝后改文、切章和远端变更。
- 在明确选择的 Provider 上验证实际结构化输出、延迟、取消和错误，记录模型、策略版本与调用成本；Provider 差异分别报告。
- 用合成或有明确授权的文本走完整手动／自动交互。不得提交私人小说、真实用户库、凭据或原始请求中的私密内容。
- Desktop UI 必须从待验收 checkout 重建，确认 bundle 来源后测试；源码检查不能替代实机。若修改触及移动端共享表面，单独验收触控、IME、键盘避让、popover portal 和活动编辑面所有权。

验收：

- `C17`：合成轨迹中的任务遗漏、过期落库／覆盖、重复领域接受、无授权自动写入为零；可重复运行并定位到具体案例。
- `C18`：真实 Provider 的成功／失败、取消、延迟、输入输出 token 和预算限制有可复核记录；不以静态 schema 测试替代实际模型验收。
- `C19`：相同写作轨迹记录有效建议数、作者采纳／拒绝、重复率、主动提示次数、手动完成时间和成本，与本轮旧行为基线比较。反馈少不能单独证明变好，采纳率不能单独代表文学质量；默认值与上线决定附具体观察依据，证据不足保持有限使用。
- `C20`：变更对应 CI／契约、公开边界、lint、typecheck、测试和能力清单检查通过；当前状态文档准确区分实现、实机验收和发布，未验收平台不宣称可用。

## 6. 实施顺序与范围控制

顺序为 **P1 → P2 → P3 → P4 → P5**。每个阶段可拆成小变更，但下一阶段的作者可见行为依赖前一阶段验收。P1 和 P2 的成果优先独立交付，避免作者等待全部自动化完成。

本轮不加入自动续写、自动全书文学批评、完整 Ambient World Model、新后台常驻进程或应用退出后继续运行。TODO 标记解析等确定性便利功能单独保留，不因它们被挂在 Copilot 下就改成模型判断；设置迁移时明确其自动开关归属，避免连带关闭／开启。

实施前再次检查工作树与相关并行修改。每次仅修改当前阶段需要的文件，不覆盖无关工作，不把本计划中的建议文件名视为已有实现。任何新增持久域或工具必须补充真实 migration／sync／capability 证据；派生证据通过对应生成器更新，不能直接改生成产物来满足计划。
